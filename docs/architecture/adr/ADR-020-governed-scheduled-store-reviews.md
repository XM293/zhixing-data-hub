# ADR-020：受治理的定时店铺复盘

- 日期：2026-08-30
- 状态：accepted
- 关联迁移：`0036_scheduled_store_reviews`

## 背景

经营分析已经能由管理者手动冻结指标与规范事实、运行 AI 或确定性降级、生成简报并把建议送入人工审批。但日常巡店依赖管理者重复发起，浏览器计时无法在无人打开页面时运行，也不能可靠处理重试、权限变化和运行审计。

## 决策

1. 新增 `StoreReviewPlan` 保存企业边界、平台范围键、IANA 时区、业务时间、运行星期、观察窗口、送审阈值、创建主体与 Actor 快照。计划不保存经营事实副本。
2. 新增 `StoreReviewScheduleRun` 关联计划、业务日、触发方式、后台任务、分析运行、简报和提案数量。定时运行按 `计划 + 业务日` 幂等，手动运行使用客户端动作幂等键。
3. API 内调度器只发现到期计划、创建运行并入队 `analysis.daily-store-review`。模型、数据查询和行动生成都不在调度循环中执行。
4. 通用 Worker 领取任务后调用领域 API。领域 API 根据计划创建人的当前数据库账号重新构造 `ActorContext`，再次检查分析、指标查询和范围权限，然后复用既有 `BusinessAnalysisRun` 与 `BusinessBrief` 用例。
5. `auto_propose_min_priority` 只控制哪些分析建议可以自动形成 `pending_approval` 提案。系统不自动批准、不创建外部写入，也不调用店铺、CRM 或 ERP。
6. 计划列表以后台任务状态投影 Worker 前置失败和重试状态；统计、台账行、尝试次数和终态时间使用同一投影，避免显示自相矛盾。
7. `/console/analysis/review-plans` 使用 API 返回的动态范围，不硬编码客户店铺；CEO/运营负责人可管理，员工和其他只读主体只能查看授权结果。

## 后果

- 手工诊断与自动巡店共享相同指标语义、规范事实、证据快照、AI Provider、简报和行动审批，不形成第二套分析真值。
- 浏览器可以关闭，业务时间和 Worker 重试仍由服务端推进；每次运行都能追溯计划、主体、范围、任务、模型、证据和提案。
- 当前本地私有部署以同库任务状态和仅本机 API 约束 Worker 内部调用。进入多主机或不可信网络前，需要独立服务身份认证，任务 ID 不能当作服务凭证。
- SQLite 只验证单进程开发体验；生产并发领取仍依赖 PostgreSQL 的事务和 `FOR UPDATE SKIP LOCKED`。
- 该纵向切片不提前关闭正式运营、通知分发或外部自动执行任务。

# ADR-009：版本化知识导入与制度生命周期

- 状态：Accepted
- 日期：2026-08-28
- 关联任务：`KNO-001`、`KNO-002`、`KNO-003`、`KNO-006`、`KNO-007`

## 背景

知识中心此前能够展示数据库种子资料、检索切片并支撑分身回答，但缺少一条用户可操作的真实写入链路。继续只增加静态页面会掩盖四个关键问题：原件重复导入、制度版本覆盖、生效时间歧义，以及平台管理员与业务负责人的职责混淆。

客户的数据结构、对象存储和知识后端尚未确定，因此首期需要稳定应用契约，同时允许原件存储、解析器和检索 provider 后续替换。

## 决策

1. 知识对象使用稳定 `document_key`，版本正文不可覆盖修改；修改内容必须创建新版本。
2. 导入服务对正文计算 SHA-256。相同内容再次导入时记录一条 `duplicate` 运行，但不创建重复版本或切片。
3. 首期同步解析 Markdown/纯文本标题并形成稳定切片；解析器名称和元数据写入运行台账，为后台 Worker 和第三方解析器保留替换点。
4. 新版本默认是 `draft`。发布命令显式写入计划生效时间；退役命令关闭版本有效区间。指定 `as_of` 的查询必须只返回一个正确的有效版本或明确无结果。
5. 同一制度的草稿、当前有效、已发布和待生效版本进入冲突比较。数值、比例和日期阈值差异标记为高优先级冲突，但不自动覆盖或阻止负责人判断。
6. `knowledge.document.ingest` 与 `knowledge.policy.publish` 分离。平台管理员可以导入但不能发布；CEO 测试主体可以发布/退役但不能导入。API 始终再次授权，前端隐藏按钮不构成安全边界。
7. 每次导入、发布和退役都保存主体、理由、`request_id`、`run_id` 和业务时间。重复发布、重复退役采用幂等结果，不生成相互矛盾的生命周期结论。
8. 浏览器只调用企业 API。知识 provider、MCP 和后续渠道不得直接写知识表，也不得自行解释生效版本。

## 当前实现边界

- 数据库迁移：`0016_knowledge_ingestion_lifecycle`。
- 页面：`/console/knowledge/ingestion`、`/console/knowledge/policies`。
- 开发环境正文暂存数据库；MinIO 原件存储仍待实现。
- 解析和索引当前同步执行；大文件、OCR 和第三方解析将在 Worker 中异步执行。
- 当前身份头仅用于本地测试主体选择；生产环境必须由正式认证会话构造 `ActorContext`。
- 当前冲突检测聚焦同一制度的可解释规则差异，不代替语义模型、跨知识空间审批或法律合规审查。

## 后果

正向结果：

- 页面、API、MCP 和分身可以引用同一个不可变版本及有效时间，不再依赖“当前版本”字符串约定。
- 客户未来替换对象存储、解析器或检索后端时，不需要改变制度生命周期和引用契约。
- 导入与发布职责分离，避免平台运维角色天然获得业务规则决定权。

代价与后续工作：

- 大文件同步解析会占用 API 请求，必须迁移到通用 Worker。
- 哈希去重目前以正文内容为准；二进制原件、附件和 OCR 派生物需要对象存储清单。
- 多人会签、撤回发布、紧急停用和跨制度冲突需要后续状态机与评测集。

# ADR-007：企业经营数字孪生采用空间投影与二维工作台双模式

## 状态

已接受，首个纵向验收切片进入产品评审。

## 背景

原 Three.js 首页只表达系统节点和连线，能够证明数据来自数据库，但不能表达企业空间、经营异常、角色协作和决策过程。单纯增加模型或动画仍会形成一次性演示，不能支撑后续真实经营数据、数字分身和受控执行。

同时，表格、配置、审批、审计和复杂分析不适合放入三维场景。项目需要保留高密度二维企业后台，并让二维与三维界面指向同一业务对象。

## 决策

### 1. 三维场景是运行投影，不是经营事实源

场景、空间、分身位置、移动路线和会议状态使用独立投影表保存。经营指标、知识、角色版本、会议证据和行动记录仍由各自领域模型负责。三维对象通过稳定业务键关联这些对象，不复制领域事实。

### 2. 使用双模式交互

- Three.js 表达园区、楼层、房间、数据流、异常位置、分身在场状态和协作过程。
- 二维工作台表达列表、详情、筛选、配置、审批、审计和证据。
- 同一空间、分身、会议和指标使用稳定键，三维选择可以打开二维详情，二维对象也可以定位回三维空间。

### 3. 首个持久化投影模型

- `TwinScene`：场景、版本和镜头预设。
- `TwinSpace`：业务空间、健康度、告警和指标绑定。
- `TwinActor`：分身外观投影、当前位置和能力摘要。
- `TwinRoute`：分身在业务空间之间的移动路径。
- `TwinMeeting`、`TwinMeetingParticipant`：会议运行状态和参会投影。
- `TwinMeetingSeat`：独立于参会人的会议席位布局、朝向、容量和占用状态。
- `TwinInteractionProfile`：三维业务对象可用动作、二维详情入口和可进入空间配置。

`0003_spatial_drilldown` 在此基础上增加可渐进装载的空间层级：

- `TwinScene.parent_scene_key`、`scene_level` 和 `entry_space_key` 定义园区、楼宇和业务空间之间的进入关系；
- `TwinHotspot` 保存空间内可选择的业务热点、稳定业务引用、严重度、位置和详情，不把业务事实硬编码进 Three.js；
- `TwinDataLayer` 保存库存风险、业务流和自动化设备等可开关图层及视觉语义；
- `asset_bundle_key` 是后续替换 glTF/VRM 资产包的稳定挂载点，首期使用程序化资产时同样保留。

### 4. 首个纵向故事

首个验收切片固定为：企业园区总览 → 进入经营空间 → 定位仓储异常 → 召集三位数字分身 → 分身沿数据库路线到场 → 会议研判 → 形成持久化决策包 → 打开二维会议台账。

会议状态使用 `scheduled → convening → in_session → decision_ready`。状态推进写入数据库并生成平台运行事件，不使用纯前端假动画伪装业务结果。

`0004_meeting_orchestration` 为会议增加 `next_transition_at`。召集操作持久化到期时间，API 生命周期内的轻量调度器负责将到期会议推进到研判态；页面只轮询最新投影。该实现是 M0 单进程基线，后续由通用 Worker 接管时保持同一持久化契约。

`0005_twin_interactions_and_seating` 把对象交互能力和会议席位持久化。前端不再按对象名称判断能否双击进入，也不再内置三个人物坐标；客户现场可通过投影数据调整可用动作、二维路由、空间入口、座位容量和人物分配。

### 5. 资产与渲染策略

首个切片使用程序化几何建立楼体、房间、设施、数据管线和统一风格分身，先验收空间比例、镜头、交互与产品价值。通过后再建立带许可证清单的 glTF/VRM 资产目录，并用 Blender 和 glTF 优化流水线替换高价值场景对象。

WebGLRenderer 是首期兼容基线；WebGPU 在兼容性和性能数据充分后再评估。桌面和移动端使用不同镜头距离和二维面板布局，但共享场景和业务契约。

### 6. 镜头与空间进入约束

- 园区、经营、仓储和会议入口使用可复位的引导镜头，保证业务导航结果稳定；引导完成后启用 `OrbitControls`。
- 工具栏提供旋转和平移分段模式：旋转模式下左键拖动旋转，平移模式下左键拖动平移；右键拖动始终平移，滚轮始终缩放。触摸端支持单指旋转与双指缩放/平移；距离和俯仰角受限，避免进入模型内部或丢失场景。
- 点击用于选择业务对象，拖动超过阈值后不触发选择；可进入空间同时提供明确按钮和三维双击入口。
- 仅业务对象参与射线命中，人物、热点、席位和空间具有明确优先级。悬停、选中和告警是三种独立视觉状态；建筑使用边框与地面选框，人物使用脚下光环，热点和席位使用独立指示环。
- 双击进入和右侧对象功能均读取 `TwinInteractionProfile`。右上角保留所选对象的二维详情入口，复杂表格、分析和审批仍在常规后台完成。
- 进入子场景只切换场景投影和控制状态，侧栏、命令面板、指标坞、经营分析和数据管理仍是常规二维后台。
- 详细场景按 `TwinScene` 独立组织。首页只创建园区，首次进入仓储或数字会议室时才创建对应子场景并在离开后复用；门店和客服作战室沿用同一契约增量实现。
- 引导镜头从当前 `TwinScene.camera_preset` 读取位置和观察点，同时兼容早期仅保存位置数组的预设；程序化场景不得再以组件常量覆盖数据库镜头。

### 7. 数字会议空间投影

- `decision-room-interior` 使用通用 `TwinHotspot` 表达证据快照、核心分歧、决策包和行动审批闸门，使用通用 `TwinDataLayer` 表达证据上下文、角色观点和决策链。
- 会议空间不复制会议领域事实。会议状态、参会人状态、独立观点和最终决策仍来自 `TwinMeeting` 与 `TwinMeetingParticipant`。
- 首期会议室使用 `boardroom-12` 的 12 席椭圆布局，桌椅朝向由持久化席位坐标计算。三位种子分身稳定分配到相隔 120 度的席位，其余席位保持可选择的空闲状态，为后续增加分身预留容量。
- `scheduled` 时分身位于会议空间入口；`convening` 时沿空间路线到席；`in_session` 时轮流进入发言态；`decision_ready` 时点亮决策输出并开放二维会议台账入口。
- 证据、观点、分歧、决策和行动分别可选择与关闭图层。三维用于理解协作过程，二维面板继续承担精确阅读、状态推进和审计跳转。
- 会议运行状态只形成导航提醒。只有用户主动进入或发起会议时镜头才跟随会议；用户切换到仓储或其他空间后不得被会议状态强制拉回。
- 决策热点在 `decision_ready` 前只返回“等待会议生成”，避免把种子数据中的演示结论提前暴露为已生成结果。

### 8. 园区尺度与容量约束

- `enterprise-campus` 2.0 使用 `72 × 48m` 的数据库空间投影，不再把六类业务空间堆叠进单栋两层展示楼。
- 数据接入、经营指挥、智能仓储、知识中心、分身工作室和数字会议使用独立建筑坐标，通过主干道、中央协作广场、装卸前场和数据流干线连接。
- 园区总览负责表达建筑关系和跨空间协作；选中建筑后使用低俯角巡视镜头并渐隐屋顶，进入按钮再装载独立业务内景，避免“定位”和“进入”混为一谈。
- 空间位置、占地、分身初始位置、跨楼路线和镜头继续由数据库投影控制。Three.js 只生成当前版本的程序化资产，不拥有空间事实。
- 中央广场首期预留 16 个分身占位点；新增分身时优先扩展投影数据和容量规则，不通过缩小数字人或继续堆叠楼层解决拥挤。
- 客户现场可按实际园区或虚拟业务拓扑重配坐标。真实仓库、办公区和会议空间可以使用不同比例，不要求与物理建筑一比一复制。

## 结果

- 3D 视觉不再与业务数据脱节，场景状态可以重放和审计。
- 常规后台能力不会被三维交互牺牲。
- 后续可以逐步替换高质量模型，而不改变业务契约。
- 场景可以从园区下钻到独立业务空间，并由数据库控制热点和图层。
- 数字会议从房间图标升级为可进入、可观察且与持久化状态机一致的协作空间。
- 需要持续维护场景版本、资产授权、性能预算和低性能设备降级策略。

# ADR-013：规范电商经营事实层

- 状态：accepted
- 日期：2026-08-29
- 决策范围：数据接入、经营事实、分析与 AI 查询边界

## 背景

数据中心已经能够保存第三方原始记录、稳定业务实体和统一指标，但仅靠这三类对象仍无法回答订单明细、SKU 毛利、退款归因、库存日快照与广告效果之间的跨域问题。若业务页面直接解析原始 JSON，客户进场后每个吉客云、CRM、广告平台或文件字段变化都会传导到页面、AI Prompt 和 MCP 工具，系统会退化为一次性项目。

主流电商开放接口通常把订单头/行、退款、库存全量或增量单据、广告日绩效拆为不同资源，并依赖源系统内稳定的订单、单据、SKU、仓库和计划键。测试沙箱采用这些接口形态，但不复制供应商代码或内部数据模型。

## 决策

在原始接入层和指标语义层之间建立平台自有的规范经营事实层，首批包含：

1. 订单事实 `commerce_order_facts`；
2. 订单行事实 `commerce_order_line_facts`；
3. 退款事实 `commerce_refund_facts`；
4. 库存日快照事实 `commerce_inventory_snapshot_facts`；
5. 广告日绩效事实 `commerce_ad_performance_facts`。

金额在接入契约中使用整数分，业务日期与带时区事件时间分离。每条事实保存 `enterprise_id`、来源系统、源 Schema 版本、平台映射版本和同步批次；稳定业务键在企业范围内唯一，重复同步执行幂等更新。

连接器负责把客户字段映射到 `contracts/data/commerce-fact-batch.schema.json`。上层经营页面、AI 分析和 MCP 工具只依赖平台契约，不得读取第三方测试字段。原始源记录继续用于审计与重放，规范事实用于明细查询与跨域计算，统一实体用于主数据，指标快照用于口径一致的聚合回答，四者保持分离。

## 运行模型

`services/mock-commerce` 是独立第三方契约沙箱，支持不同体量和失败场景。数据同步先保存原始记录，再由同一连接器批次写入规范事实；写入顺序保证订单先于订单行，所有事实关联实际同步批次。

`GET /api/v1/data-center/commerce-operations` 从事实表计算店铺贡献、订单履约漏斗、退款率、库存风险、广告 ROI、跨域异常和血缘资产。该接口是数据库运行视图，不是前端 Fixture。驾驶舱概览只聚合事实总量，明细继续由数据中心承接。

## 客户适配

客户实施先发现来源能力与字段，再为来源创建版本化映射；真实来源可以是开放 API、数据库/CDC、批量文件或消息事件。字段差异应封装在连接器和映射版本中，不能通过增加客户专属页面分支解决。源系统没有某一事实时允许该资源为空，上层必须明确显示数据缺口。

## 后果

- 优点：真实数据结构变化被限制在接入边界，经营分析、分身、会议和 MCP 可以复用稳定契约；
- 优点：每个数字均可追溯到来源、Schema、映射与同步批次；
- 代价：需要维护事实契约、幂等键、迟到数据与对账规则；
- 限制：当前模拟数据验证的是结构、体量和链路，不代表客户口径对账、年度留存、峰值并发或生产容量已经通过。

本 ADR 不改变正式 `DAT-*` 任务依赖，也不将产品全景验收门自动置为完成。

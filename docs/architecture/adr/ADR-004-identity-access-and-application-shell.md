# ADR-004：身份、访问控制与管理台壳子

- 状态：Accepted
- 日期：2026-08-24
- 决策范围：M0 身份权限补强及后续全部里程碑

## 背景

知行数枢面向 CEO、部门经理、员工、渠道机器人和智能体运行时。同一份制度、经营指标或工具，不同人员的可见范围和可执行动作不同。企业私有化部署只解决部署边界，不能替代企业内部授权。

如果先实现分身、知识检索和 MCP，再补权限，用户身份、部门范围和授权信息会散落在每个模块中。尤其是 CEO 分身面向普通员工时，分身的表达身份不能被误认为 CEO 本人的数据权限。

## 决策

### 1. 保留稳定企业边界

首期默认一套部署服务一个企业，不建设 SaaS 计费和跨租户运营后台；但核心实体、任务、证据、运行和审计记录必须携带稳定的 `enterprise_id`。集团、子公司和业务单元通过组织与数据范围表达，不通过复制用户体系表达。

### 2. 身份、岗位、分身和访问角色严格分离

| 概念 | 用途 | 不代表 |
|---|---|---|
| `Principal` | 可被认证、授权和审计的主体，包括人员、服务账号和智能体执行身份 | 具体员工资料 |
| `User` | 企业内的人员账号和状态 | 部门岗位或权限集合 |
| `OrgUnit` / `Position` / `Membership` | 组织、岗位以及人员在组织中的任职关系 | 自动获得所有数据权限 |
| `AccessRole` | 可分配的访问权限集合 | 岗位职责或管理风格 |
| `RoleTemplate` / `RoleTwin` | 岗位知识、个人风格、记忆和回答边界 | 登录账号或访问角色 |
| `ChannelIdentity` | 飞书等渠道身份到内部主体的映射 | 通过姓名猜测的用户身份 |

代码、数据库和界面不得使用含糊的 `role` 同时表示访问角色与角色分身。访问控制统一使用 `AccessRole`，智能分身统一使用 `RoleTwin`。

### 3. 使用 RBAC 与数据范围组合授权

权限键采用 `<domain>.<resource>.<action>`，例如：

- `knowledge.policy.read`
- `knowledge.policy.publish`
- `metric.query.execute`
- `memory.candidate.review`
- `action.proposal.approve`

`AccessRole` 聚合权限，`ScopeGrant` 限定权限适用范围。首期范围至少支持：

- 整个企业；
- 当前组织或组织子树；
- 指定店铺或业务单元；
- 指定数据源、知识空间或角色分身；
- 仅本人创建或本人负责的对象。

授权规则采用默认拒绝。明确拒绝优先于允许；多个约束同时存在时取交集，不取并集。页面隐藏只改善体验，API、MCP、Worker 和 Action 执行点必须重新检查权限。

### 4. 所有入口使用统一 ActorContext

认证完成后生成版本化 `ActorContext`，至少包含：

```text
enterprise_id
actor_principal_id
on_behalf_of_principal_id
identity_source
membership_ids
permission_set_version
channel
request_id / run_id
```

- 人直接操作时，`actor` 与 `on_behalf_of` 相同。
- 分身或自动任务运行时，`actor` 是实际执行主体，`on_behalf_of` 是发起或授权该运行的人员。
- 后台任务保存发起者和权限快照；产生外部状态变化前必须按当前权限重新授权。
- 不允许客户端自行声明部门、访问角色或数据范围。

### 5. 分身和智能体使用权限交集

一次运行的有效能力为：

```text
调用者权限
∩ RoleTwin 能力边界
∩ 渠道允许能力
∩ 工具风险与行动审批规则
```

RoleTwin 可以影响分析职责、可使用的知识和表达方式，但不能提升调用者权限。普通员工询问 CEO 分身时，只能读取该员工原本可访问的数据。数字会议使用发起人授权冻结的证据快照，参会分身不能自行扩大范围。

### 6. 认证提供者通过适配器接入

领域层只识别内部 `Principal` 和 `ChannelIdentity`。首期提供本地开发管理员认证；生产接入飞书、OIDC 或反向代理身份时使用适配器，不把外部 `open_id`、令牌结构或供应商会话写入领域模型。

### 7. 菜单是授权结果的投影

管理台建立统一应用壳子。后端通过当前主体能力返回导航投影，前端据此显示中心、菜单和操作按钮，并提供登录、无权限、未找到和会话失效页面。

菜单键保持稳定并指向产品导航，权限键指向业务能力。二者可以映射，但不得把菜单键当作 API 权限。

### 8. 授权审计与运行日志分离

`AuthorizationDecision` 记录主体、资源、动作、范围、策略版本、允许或拒绝及原因。`AuditEvent` 记录账号、组织、权限、审批和关键配置变更。运行日志可以进入统一日志系统，但不能替代可查询、可保留的领域审计记录。

## 首期实现边界

M0/M1 必须完成：

1. 企业、人员、组织、岗位、任职和渠道身份的稳定模型。
2. `AccessRole`、`Permission`、`ScopeGrant` 和 `ActorContext` 契约。
3. 本地管理员认证和可替换认证适配器接口。
4. API 权限守卫、管理台壳子、授权菜单和 401/403 状态。
5. MCP、后台任务和 Action 可以复用的授权接口。
6. 授权决策和关键管理变更审计。

首期不建设复杂策略语言、跨客户 SaaS 管理后台、字段级动态脱敏或外部 IAM 产品。出现大量条件策略后再评估 Casbin、OpenFGA 或其他策略引擎，领域契约不依赖其内部模型。

## 影响

- `FND-007` 只负责企业、用户、组织、岗位和任职关系，不再使用含糊的“角色模型”。
- 新增 `IAM-*` 任务负责身份契约、认证、授权、菜单、渠道映射和审计。
- `RoleTwin`、知识查询、指标查询、Agent Runtime、MCP 和 Action 任务必须显式依赖相应 IAM 能力。
- `EnterpriseEntity` 不再重复拥有用户、部门和岗位，只保存业务实体以及对组织主体的稳定引用。

## 验收

- 未认证访问受保护 API 返回统一 401；已认证但无权访问返回统一 403。
- 部门经理只能查询授权组织或店铺范围，CEO 分身不会扩大提问者权限。
- Web 菜单、API、MCP 和后台任务对同一主体得出一致授权结果。
- 飞书身份必须通过显式映射绑定内部主体。
- 权限变更、拒绝、审批和关键配置变更均可审计。

# ADR-016：受治理客户 360 事实与统一查询边界

- 日期：2026-08-30
- 状态：accepted
- 关联迁移：`0032_customer_360_facts`

## 背景

CRM 客户主档、客户行为触点和 ERP 交易事实具有不同的来源权威性、更新频率和迟到修正规则。只把客户保存为通用 `BusinessEntity.attributes` 无法提供稳定约束、独立清理和可审计血缘；把 CRM 成交金额直接当作交易真值，则会绕过已经建立的规范订单与退款事实层。

## 决策

1. 新增 `CustomerProfile` 作为 CRM 当前客户主档投影，保存稳定客户键、归属来源店铺、会员等级、生命周期、获客渠道、活跃时间、流失风险、触达同意和标签。
2. 新增 `CustomerTouchpointFact` 保存可重复同步的行为事实，触点类型、发生时间、渠道、活动、价值和来源属性与客户主档分离。
3. 交易次数、成交金额和退款金额只从 `CommerceOrderFact` / `CommerceRefundFact` 汇总；CRM 不覆盖 ERP 交易真值。
4. 连接器通过 `authoritative_fact_types` 分别声明客户主档和触点资源是否完整取得。完整批次可清理同源缺失旧数据，部分失败只更新成功的事实族并保留其他历史数据。
5. `/api/v1/data-center/customer-360`、单客详情接口、管理台和 `query_customer_360` MCP 共用一个领域服务、`customer.profile.read` 权限和平台范围到来源店铺键的映射。单客不存在和超出范围统一返回不可见，MCP 不直接查询数据库私表。
6. 单客详情只组合已治理的客户主档、触点、订单和退款，不建立第二套交易真值。统一时间线保留来源、同步批次和稳定证据键。
7. 当前运营建议使用版本化确定性 Playbook，根据生命周期、风险、活跃、退款和同意状态生成。每项建议必须保存证据键、适用资格和动作边界；结果不是模型自由推断，也不得直接触发优惠、消息、补偿或外部写入。
8. 每个客户系统继续保留 `source_schema_version`、`mapping_version`、`sync_run_id` 和企业边界。客户现场字段变化在连接器与版本化映射中吸收。

## 结果

- 页面、AI 与 MCP 获得相同的客户价值、生命周期和行为结果，并可追溯到 CRM 与 ERP 的实际同步批次。
- 门店账号只能读取授权门店，企业范围授权可以汇总全部已映射来源店铺。
- 客户画像可以独立演进而不污染通用实体目录，也不会复制订单真值。
- 运营、AI 和 Codex 可通过同一只读契约获得可重放的单客上下文，后续模型建议仍需遵守证据和动作边界。
- 当前同步仍是测试纵向切片；生产环境还需要增量游标、身份合并、同意变更历史、迟到事件和容量基线。

## 否决方案

- **万能客户 JSON 表**：缺少稳定约束、血缘和事实族清理语义。
- **CRM 直接提供成交指标**：会与 ERP 订单/退款产生双重真值。
- **MCP 直连 CRM 或数据库**：会绕过平台权限、范围映射和调用审计。

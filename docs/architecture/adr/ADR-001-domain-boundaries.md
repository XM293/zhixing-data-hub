# ADR-001：产品领域边界与模块命名

- 状态：Accepted
- 日期：2026-08-24
- 决策任务：FND-001
- 适用里程碑：M0 及后续全部版本

## 背景

知行数枢既要承载企业经营数据和正式制度，也要承载角色记忆、智能体运行、数字会议和业务行动。如果仅按页面或开源组件划分代码，系统会很快退化为一个同时处理数据同步、RAG、Prompt 和业务写入的“大 Agent 服务”，无法保证事实口径、版本追踪和运行时替换。

本 ADR 固定产品领域边界、数据所有权、依赖方向和实现命名。物理部署可以从模块化单体演进，但领域边界不得因首期共用数据库或进程而消失。

## 决策

### 1. 领域模块

| 领域模块 | 规范模块键 | 独占职责 | 不承担的职责 |
|---|---|---|---|
| 身份与组织 | `identity` | 企业边界、主体、用户、组织、岗位、任职、渠道身份映射、访问角色、权限和数据范围 | 角色分身内容、渠道消息处理 |
| 数据源接入 | `source` | 来源注册、连接器配置、同步游标、任务和错误统计 | 经营指标定义、上层业务分析 |
| 企业实体 | `entity` | 企业稳定 ID、店铺/商品/SKU/客户等规范实体、外部 ID 映射 | 源系统私有字段透传 |
| 指标与经营事实 | `metric` | 规范事实、指标定义、维度、口径、查询和对账 | 自由文本知识检索 |
| 正式知识 | `knowledge` | 制度原件、解析、版本、生效区间、发布状态、检索和引用 | 个人偏好、未审核聊天 |
| 角色记忆 | `memory` | 记忆候选、审核、版本、启停、检索和冲突标记 | 当前制度和经营事实真值 |
| 角色分身 | `role-twin` | 岗位模板、个人实例、职责边界、风格和角色版本 | 直接持有知识库或模型供应商内部 ID |
| 证据 | `evidence` | 引用规范、EvidenceSnapshot、数据和知识版本冻结、可重放信息 | 生成业务判断或执行动作 |
| 智能体运行时 | `agent-runtime` | AgentRun、运行事件、上下文预算、模型/运行时适配和工具调用编排 | 企业事实所有权、业务写入审批 |
| 数字会议 | `meeting` | 议题、独立分析、主张、质询、分歧、决策包和复盘 | 修改指标口径或直接执行行动 |
| 行动执行 | `action` | ActionProposal、审批、幂等执行、结果、失败和补偿说明 | 任意 SQL、绕过审批的外部写入 |
| 渠道 | `channel` | Web、飞书及后续渠道的消息规范、外部身份声明提取和展示适配 | 持久身份映射、复制问答、会议或行动业务逻辑 |
| 反馈与评测 | `evaluation` | 反馈、黄金集、回归结果、版本对比和业务试点指标 | 在线业务真值和生产流程编排 |
| 运行运营 | `operations` | 配置、日志、运行 ID、健康状态、成本和告警 | 修改领域规则、拥有授权决策或替代领域审计记录 |

`analysis` 是由角色分身、指标、证据和运行时共同组成的应用能力，不单独拥有经营事实。需要独立代码时使用应用用例目录 `usecases/analysis`，不得复制 `metric` 的指标定义和查询逻辑。

### 2. 四类资产必须物理可区分

即使首期都使用 PostgreSQL，也必须通过不同表、仓储接口和对象类型区分：

1. 经营事实：由 `source`、`entity`、`metric` 管理。
2. 正式知识：由 `knowledge` 管理，原件进入对象存储。
3. 角色记忆：由 `memory` 管理，聊天只能先形成候选。
4. 运行与行动记录：分别由 `agent-runtime`、`meeting`、`action` 管理。

任何通用检索或上下文服务都只保存这些资产的稳定引用，不成为新的真值所有者。

所有四类资产都必须带有稳定 `enterprise_id`，并在访问时使用可信 `ActorContext`。身份与授权是跨领域控制面，不改变四类业务资产的真值归属。

### 3. 产品导航与领域映射

| 客户可见导航 | 主要领域模块 | 说明 |
|---|---|---|
| 企业数据中心 | `source`、`entity`、`metric` | 数据源、同步、实体映射、指标目录和对账 |
| 企业知识中心 | `knowledge`、`evidence` | 制度导入、版本发布、引用和冲突提示 |
| 角色分身中心 | `role-twin`、`memory`、`agent-runtime` | 岗位模板、个人实例、记忆审核、Prompt/运行配置 |
| 数字会议中心 | `meeting`、`evidence`、`role-twin` | 议题、过程、决策包和复盘 |
| 智能分析中心 | `metric`、`evidence`、分析用例 | 问数、诊断、简报、预警和运营指导 |
| 行动与执行中心 | `action`、工具网关 | 草拟、审批、执行、结果和补偿 |
| 平台管理 | `identity`、`channel`、`evaluation`、`operations` | 组织、渠道、评测、运行记录和配置 |

导航是多个领域能力的投影，不是新的数据所有权边界。未实现功能可以显示“规划中”，但不得创建返回模拟成功结果的伪功能。

### 4. 依赖方向

代码依赖遵循：

```text
渠道 / Web / MCP / 连接器
          ↓
应用用例（use cases）
          ↓
领域服务与自有契约
          ↓
仓储和外部组件适配器
```

跨领域调用必须经过公开应用接口或版本化契约，禁止直接读取另一个领域的表。允许的核心依赖为：

- `role-twin` 可以引用 `identity` 的稳定 ID，但不复制组织数据。
- `RoleTwin` 不得保存或继承 `AccessRole`；分身运行权限取调用者、分身能力、渠道和工具规则的交集。
- `channel` 只提取外部身份声明，持久 `ChannelIdentity` 映射由 `identity` 管理。
- API、MCP、Worker 和 Action 必须通过 `identity` 的公开授权接口消费 `ActorContext`，不得各自解释岗位或部门权限。
- `evidence` 可以引用 `knowledge`、`metric` 和 `memory` 的不可变版本。
- `agent-runtime` 通过 Provider/Tool 接口读取上下文，不拥有来源数据。
- `meeting` 使用固定的 `evidence` 快照和已发布 `role-twin` 版本。
- `action` 接受运行时或会议产生的提议，但只有自身可以批准和记录写操作。
- `channel` 只调用应用用例，不直接访问知识、指标或模型后端。

任何反向依赖都必须通过事件或稳定接口表达，并新增 ADR 说明原因。

### 5. 代码命名

- 产品和文档使用中文中心名称。
- 契约键、事件和 URL 使用小写短横线，如 `role-twin`、`agent-run.started`。
- Python 包使用下划线，如 `role_twin`、`agent_runtime`。
- TypeScript 包使用 `@zhixing/<module>`，如 `@zhixing/contracts`。
- 数据库表使用领域前缀，如 `knowledge_policy_version`、`memory_candidate`、`action_execution`。
- 外部系统适配器使用 `<provider>-adapter`，不得以供应商名称命名领域模块。

## 实现约束

1. 首期使用模块化单体；模块可共用进程和数据库实例，但不共用领域模型文件或私有仓储。
2. OpenViking、WeKnora、RAGFlow、TencentDB-Agent-Memory、Mem0、Codex 等均只能位于适配器层。
3. MCP 工具调用应用服务；MCP 不是数据层或跨领域后门。
4. UI 菜单、API 标签、代码目录和任务 Epic 应使用本 ADR 的规范名称。
5. 新增领域或改变数据所有权必须新增 ADR，并同步产品导航和任务索引。
6. 访问角色统一命名为 `AccessRole`，禁止与 `RoleTemplate`、`RoleTwin` 或岗位 `Position` 混用。

## 影响

### 正面影响

- 管理者分身可以作为首个纵向切片开发，而不会成为系统唯一内核。
- 数据、制度和记忆发生冲突时，可以确定真值所有者和版本优先级。
- Codex 或其他智能体运行时可替换，不影响角色、证据、会议和行动记录。
- 后续拆分 Worker 或服务时已有稳定边界，无需先重构业务所有权。

### 代价

- 首期需要定义更多接口和稳定 ID，不能直接把开源项目对象暴露给页面。
- 跨模块查询需要应用用例或只读投影，不能随意联表实现页面。
- 领域边界测试和契约版本管理会增加早期工作量。

## 验收对应

- 已覆盖数据、知识、记忆、角色、证据、智能体运行、会议和行动边界。
- 已明确六大业务中心及平台管理导航与领域模块的映射。
- 已规定数据所有权、依赖方向、命名和开源组件接入位置。

# ADR-021：选择性吸收 PigX 企业管理能力

- 日期：2026-08-30
- 状态：accepted
- 参考版本：已授权 PigX 5.9.0 微服务源码包
- 关联指南：`docs/development/06-pigx-selective-capability-integration-guide.md`

## 背景

知行数枢的核心目标是企业数据中心、指标语义、知识、角色记忆、数字分身、MCP 和受治理行动。当前项目采用 FastAPI/Next.js 模块化单体和统一 `ActorContext` 授权模型。

PigX 5.9.0 提供了成熟的用户、组织、岗位、角色、菜单、审计、通知、文件、流程和管理台交互，但其运行时是 Java/Spring Cloud 微服务体系，权限主要围绕传统角色菜单模型，数据库也与知行数枢的 AI 数据中心模型不同。

如果整包引入，会产生两套身份、菜单、任务和运维体系，增加部署和数据一致性成本，也不能直接解决指标、知识、记忆和智能体证据问题。

## 决策

1. 知行数枢保留现有模块化单体、数据中心和 AI 核心架构。
2. PigX 只用于参考企业后台功能、交互模式和可选的外部身份输入。
3. 用户、组织、岗位、角色、菜单、审计、配置、通知和文件等选定能力使用知行数枢自有契约重新实现。
4. 不将 PigX 的内部 ID、`sys_*` 表、Spring Bean 或私有 API 写入知行数枢领域代码。
5. 不把 Nacos、Gateway、Seata、Sentinel、Quartz、XXL-Job、Flowable 等作为首期依赖。
6. 知行数枢身份授权模型是唯一权限事实来源；所有 Web、API、渠道、Agent、MCP、Worker 和 Action 都必须使用可信 `ActorContext`。
7. 不开发 PigX 专用导入适配器，不运行 PigX 管理侧车；客户旧系统迁移按实际数据结构创建通用连接器或一次性迁移任务。

## 选定吸收范围

- P0：用户、组织、岗位、访问角色、菜单/按钮投影、API/动作权限、审计。
- P1：本地会话、SSO 适配接口、配置字典、通知、文件元数据、批量导入导出。
- 条件引入：复杂工作流、可靠长任务、报表平台、代码生成和外部身份平台。
- 明确排除：整套微服务基础设施、双调度器、PigX 数据库作为主库、与首期无关的微信/支付业务。

## 关键模型原则

- `AccessRole`、`Position`、`RoleTwin` 三者永远分离。
- 菜单和按钮只是权限投影，后端资源、动作和数据范围才是授权依据。
- PigX `sys_tenant` 只有在语义一对一时才可以辅助映射到 `Enterprise`，不能默认替代企业边界。
- 通用批量交换必须经过预检、逐行校验、幂等写入和审计，不接受 PigX 内部表作为领域契约。
- 正式制度、经营事实、角色记忆和 AI 运行记录不进入通用平台配置表。

## 后果

### 正面

- 保留知行数枢数据中心和 AI 架构的独立性。
- 用成熟后台产品经验补强组织、权限、菜单和审计能力。
- 可以在当前技术栈内统一人、分身、渠道、MCP 和 Worker 的授权。
- 后续只按真实需求评估独立外部系统或组件，不默认引入 PigX 运行时。

### 代价和风险

- 选定功能需要重新实现，不能直接获得 PigX 的全部代码收益。
- 若客户要求保留外部管理系统，需要单独维护版本兼容和故障降级边界。
- PigX 源码测试覆盖不足，所有吸收能力必须在知行数枢补齐测试。
- 任何新基础设施都可能增加部署复杂度，必须用实际负载证明必要性。

## 重新评估条件

出现以下条件之一时，重新创建 ADR 评估外部系统集成，不自动恢复 PigX 适配路线：

- 客户要求必须沿用 PigX 的认证、组织或审批服务。
- 当前管理台在组织、权限、配置或流程规模上达到自有实现的维护瓶颈。
- 任务执行需要跨天恢复、补偿和多系统事务，现有 Worker 无法满足。
- 需要独立团队、独立发布周期和独立容量扩展。

# 经营分析与版本化简报

状态：Implemented slice  
迁移：`0024_business_analysis_and_briefs`、`0036_scheduled_store_reviews`

## 目标

经营分析中心把数据中心已经治理的指标转换为可复核的经营诊断，而不是让模型直接访问业务库或根据前端样例自由生成结论。首个纵向切片覆盖店铺诊断和日报，后续企业复盘、周报、部门分析与岗位指导复用同一运行契约。

## 运行链路

```text
ActorContext
  -> 服务端授权范围
  -> MetricQueryService + CommerceFactQueryService
  -> EvidenceSnapshot（冻结指标序列与规范经营事实）
  -> 确定性风险基线
  -> 结构化模型推理或证据降级
  -> BusinessAnalysisRun
  -> BusinessBrief（按业务键递增版本）
  -> 数字会议 / 人工行动提案
```

1. `/api/v1/analysis/studio` 只返回调用主体可以读取的门店或企业范围、历史分析和简报。
2. `/api/v1/analysis/store-reviews` 同时要求 `analysis.run` 与 `metric.query.execute`，并再次验证请求范围。
3. 服务使用统一指标查询服务读取 GMV、订单、退款率和广告 ROI 序列，并通过版本化范围映射读取订单、退款、库存和广告规范事实，不接受客户端传入事实数值。
4. 查询结果冻结为证据快照；指标序列、经营汇总和具体异常使用同一组 `E1...En` 编号，分析只能引用该快照内项目。
5. 模型返回结构化事实、推断、风险、建议和未知项。引用不存在、结构不合法、超时或模型不可用时，系统使用确定性证据降级并保存原因。
6. 完成的运行不可修改；相同企业内的幂等键返回原运行。每次新运行自动生成对应业务日简报，版本号递增且旧版本保留。

## 受治理自动巡店

`0036_scheduled_store_reviews` 在同一分析用例外增加计划、调度运行与 Worker 编排，不另建一套诊断逻辑：

```text
StoreReviewPlan（范围 / IANA 时区 / 运行日 / 业务时间 / 送审阈值）
  -> API 调度器只识别到期计划并幂等入队
  -> BackgroundJob(analysis.daily-store-review)
  -> 通用 Worker 领取并调用领域执行入口
  -> 重新解析计划创建人的当前账号、权限和数据范围
  -> BusinessAnalysisRun + EvidenceSnapshot + BusinessBrief
  -> 可选 ActionProposal(status=pending_approval)
  -> StoreReviewScheduleRun 回写结果和审计关联
```

- `GET/POST /api/v1/analysis/review-plans` 返回当前主体的动态范围、计划、统计与最近 100 次运行；页面不硬编码客户店铺键。
- 暂停、恢复和立即运行都使用动作幂等键；暂停/恢复另外校验乐观版本。定时运行按 `计划 + 业务日` 幂等。
- 调度器不运行模型，浏览器也不承担计时。只有 Worker 领取成功后才调用领域执行；API 仍是权限、数据冻结、AI 和结果写入的唯一真值边界。
- 运行时要求计划创建主体账号仍有效，并重新检查 `analysis.run`、`metric.query.execute` 和范围授权。创建计划时的 Actor 快照只用于审计，不能替代当前授权。
- `auto_propose_min_priority` 为 `off`、`urgent` 或 `high`。命中阈值只生成待审批提案，不自动批准、不创建外部写入凭证。
- Worker 在调用 API 前失败时，计划台账会从后台任务投影失败状态、尝试次数和完成时间；顶部统计使用同一投影视图，避免把终态失败误计为排队中。

## 领域边界

- `BusinessAnalysisRun` 保存一次计算和推理事实，包括授权主体快照、指标快照、证据引用、模型信息与降级原因。
- `BusinessBrief` 是面向阅读和流转的版本化文档，只引用来源分析运行，不复制或覆盖指标真值。
- `EvidenceSnapshot` 负责可重放证据；它不是长期指标仓库，也不替代数据血缘。
- 数字会议可以消费分析运行，行动中心可以消费人工确认后的决策包；分析建议不能直接调用 R1/R2/R3 工具。
- 角色记忆可以影响表达和管理偏好，不能更改指标、风险阈值或授权范围。

## 权限模型

| 角色 | 读取授权范围分析 | 发起分析 | 跨范围读取 | 修改历史运行 |
| --- | --- | --- | --- | --- |
| CEO | 是 | 是 | 仅企业范围 | 否 |
| 部门经理 | 是 | 是 | 否 | 否 |
| 员工 | 是 | 否 | 否 | 否 |
| 平台管理员 | 是 | 否 | 否 | 否 |

前端菜单和按钮只是权限投影。API 以可信 `ActorContext` 做最终决策，不能采用请求体中的角色、企业或数据范围。

## 数据接口适配

分析层只依赖稳定指标键、规范经营事实和查询契约，不依赖吉客云、CRM 或客户数据库字段。平台范围键与客户外部店铺键通过 `DataScopeMapping` 解析；门店库存没有可靠归属映射时保持未知，不能把企业库存下放到门店。实施期的新系统通过连接器、原始区、映射版本和指标定义接入；只要保持这些契约，经营诊断页面、Prompt 和 MCP 不需要随客户表结构重写。缺少数据时必须标注未知，不能由模型补值。

## 验收范围

- 数据库迁移和重复升级通过，空库与已播种库均可运行。
- 正常模型和证据降级均生成可追溯运行；所有指标与经营事实引用命中冻结快照。
- 同一幂等键不重复写入，多次诊断形成递增简报版本。
- CEO 和经理只能运行授权范围，员工与平台管理员发起运行返回 403。
- 诊断和简报在桌面、超宽工作站和移动视口无页面级溢出，加载、空、失败、只读状态清楚。

当前切片证明“统一指标 -> 证据 -> 分析 -> 简报 -> 受治理定时调度”链路成立，不代表生产经营分析完成。真实阈值治理、指标黄金集、通知分发、跨店归因与生产规模仍需后续任务验收。

# 系统总体架构 v0.1

## 架构策略

采用“逻辑分层完整、物理部署克制”的策略。首期是模块化单体加后台任务，不为了未来规模提前拆分大量微服务；领域契约稳定后，可按数据量、团队边界和可靠性要求独立部署。

身份与访问控制是贯穿全部层级的控制面：Web、渠道、API、MCP、Agent Runtime、Worker 和 Action 都使用同一 `ActorContext` 和授权服务。菜单隐藏不构成授权，任何数据读取或外部写入都在服务端执行资源、动作和数据范围检查。

首期默认一个私有化部署服务一个企业，但全部核心记录保留稳定 `enterprise_id`，用于集团组织、业务单元隔离和未来部署演进。

## 四类核心资产

### 经营事实

订单、销售、退款、库存、广告、毛利、客户、供应商等结构化记录。保存来源系统、业务时间、同步时间和转换版本，通过统一指标语义提供查询。

### 正式知识

制度、SOP、KPI定义、FAQ和正式会议结论。必须保留原件、解析版本、审批状态、生效区间和引用定位。

### 角色记忆

经过审核的管理偏好、历史决策、表达风格、案例和反例。角色记忆不覆盖当前制度和经营事实，只作为分析和表达的补充上下文。

### 运行与行动记录

会话、提示词版本、模型、工具调用、证据快照、会议过程、行动提议、审批和执行结果，用于复盘、评测和故障诊断。

## 身份与访问控制面

身份控制面管理企业、主体、用户、组织、岗位、任职、渠道身份、访问角色、权限、数据范围、委托和授权审计。它不成为第五类业务真值资产，也不复制制度、指标或角色记忆。

一次智能体运行保存发起人、实际执行主体和权限策略版本。RoleTwin 只定义职责、知识和表达边界，不能授予账号权限。

## 首期物理部署

- `PostgreSQL`：企业身份、授权配置、业务配置、领域数据、制度元数据、记忆候选、任务和审计记录。
- `pgvector` 或知识产品内置向量能力：语义检索索引。
- `MinIO/S3兼容对象存储`：制度原件、聊天导出、附件和数据快照。
- `Redis`：仅在需要时用于任务队列、短期缓存和会话协同。
- `WeKnora POC`：首选知识产品壳和解析检索候选。
- `Codex Runtime Adapter`：首个智能体执行适配器。
- `Next.js + Python API`：管理台和模块化后端的默认候选，最终由 ADR 确认。

数据规模、查询延迟或并发证明 PostgreSQL 不再适用时，再引入 ClickHouse 或专用仓库；可靠长任务数量增加后，再评估 Temporal。

## 数据访问方式

不同数据采用不同接入方式：

1. 分析事实复制：订单、广告、库存等进入分析存储，支持历史分析和对账。
2. 实时查询：少量强实时状态通过源系统 API 读取。
3. 文档读取：保留原件，并建立解析和检索索引。
4. 写入动作：只通过源系统正式接口或受控自动化执行，不直接写分析库。

所有访问方式先解析 `ActorContext`，再将有效企业、组织、店铺、知识空间或对象范围传给领域服务。适配器不得绕过范围直接返回源系统全部数据。

## 运行时解耦

领域层只依赖以下抽象：

```text
AgentRuntime
  start(run_spec)
  resume(run_id, input)
  stream(run_id)
  cancel(run_id)

ModelProvider
EmbeddingProvider
RerankerProvider
MemoryProvider
ToolGateway
```

上述运行时接口同时接收可信 `ActorContext`。运行时和模型不能通过 Prompt、自报身份或工具参数提升权限。

首期实现 `CodexRuntimeAdapter`。后续可以加入其他模型、Agents SDK 或本地模型适配器，不改变角色、会议、证据和行动领域模型。

## 部署演进

### M0-M1：模块化单体

单一 Web、单一 API、通用后台 Worker、PostgreSQL、对象存储和可插拔知识服务。Web、API 和 Worker 共用身份授权契约，不各自维护权限逻辑。

### M2：独立数据与智能体 Worker

连接器、文档解析、Agent Runtime 和经营查询按负载独立扩容，但保持同一契约。

### M3：可靠工作流和多存储

当跨小时/跨天任务、补偿流程和大规模数据查询出现后，引入 Temporal、专用分析存储和独立元数据服务。

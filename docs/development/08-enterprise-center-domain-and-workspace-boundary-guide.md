# 企业中心域与岗位工作台边界重构指南

- 文档编号：DX-008
- 版本：0.1
- 状态：开发指导稿
- 适用产品：知行数枢 · 企业数据智能运营中枢
- 编写日期：2026-09-03
- 关联文档：`DX-007`、`FND-001`、`UIA-006`、`UIA-007`、`UIA-008`、`UIA-009`、`DOM-001`、`IAM-003`

> 本指南修正岗位工作空间实现后暴露出的产品边界问题。它定义数字孪生首页、岗位工作台、业务能力中心、数据中心、知识中心、AI 中心和平台管理之间的职责，不要求一次性实现所有中心。后续开发以此文档作为导航、路由、权限、数据模型和读模型拆分的共同依据。

## 1. 结论

按岗位呈现差异化工作台是正确的，但岗位工作台不应替代业务中心。当前 `DX-007` 已经完成了工作空间的服务端投影、权限交集和上下文传递；`DX-008` 进一步明确中心域边界，解决以下问题：

1. 数据中心的技术维护内容与经营事实、客户 360 等业务数据产品不能继续作为同一层级的 Tab。
2. 数字孪生应是登录后的企业空间入口；岗位工作台是独立的岗位视图，不应取代数字孪生首页。
3. 知识中心只管理知识资产和记忆候选，业务动作必须回到运营、客户、组织或其他业务中心。
4. 经营事实属于标准化经营数据产品，不能简单塞进运营中心，也不应与数据源、同步任务混在数据基础中心。
5. “中心”是业务责任、数据边界、API、读模型、权限和审计的组合，不等于一个页面或一个视觉卡片。
6. 多子公司场景必须从现在开始扩展集团、法人企业、业务单元、组织和店铺边界，不能把现有 `enterprise_id` 误当成集团 ID。

最终关系应稳定为：

```text
数字孪生首页 = 企业空间入口
岗位工作台   = 岗位信息聚合与下一步动作
业务中心     = 真实业务流程与领域数据
数据/知识/AI = 数字底座与共享能力
平台管理     = 身份、权限、运行和系统控制面
```

## 2. 不可破坏的架构原则

### 2.1 工作空间不是权限

`WorkspaceProfile` 只能决定指标优先级、待办排序、快捷入口、默认视图和场景节点，不能授予新的权限或扩大数据范围。所有请求仍由可信 `ActorContext`、`AccessRole` 和 `ScopeGrant` 重新授权。

### 2.2 中心域拥有业务责任

每个中心必须有明确的：

- 业务负责人和事实来源；
- 写入入口与状态机；
- 查询 API 与版本化 Read Model；
- 资源、动作和数据范围权限；
- 审计事件和失败语义；
- 可被工作台、AI、MCP 和数字孪生引用的稳定业务键。

工作台可以聚合中心的读模型，但不复制中心的写入逻辑和业务事实。

### 2.3 数据基础与数据产品分层

数据基础中心负责接入、同步、模型、质量和血缘；数据产品中心负责把这些资产整理成经营事实、客户 360、店铺 360 和指标服务。业务中心消费数据产品，不直接读取第三方源系统字段。

### 2.4 体验分层

- 数字孪生承担空间化导航和全局状态感知。
- 二维后台承担密集数据阅读、筛选、编辑、审批和异常处理。
- 3D 场景中的不可逆动作必须跳转到二维页面或进入明确的确认流程。
- 没有 WebGL、设备性能不足或移动端不适合沉浸式操作时，必须提供等价二维视图。

### 2.5 多公司边界优先于视觉聚合

集团汇总、子公司明细、组织范围、店铺范围和客户范围必须显式标识。任何“集团视图”都必须说明统计范围、合并口径、币种、业务日期和数据截至时间，不能把多个主体的数字无提示地相加。

### 2.6 页面文字规则继续有效

界面文字只能服务于业务数据、字段、状态、操作、校验、错误和必要空状态。不得在中心首页或工作台添加架构说明、功能介绍、教程、演示旁白或描述界面本身的文字。中心职责写在本指南和产品文档中，不写成页面上的营销文案。

## 3. 核心对象关系

```text
Principal / UserAccount
        │ 登录主体
        ▼
EnterpriseMembership ── 当前集团/法人企业/业务单元上下文
        │
        ├── Position（岗位与任职）
        ├── AccessRole（资源、动作、范围权限）
        └── ScopeGrant（集团、企业、组织、店铺等范围）
                │
                ├── WorkspaceProfile（岗位视图，不授予权限）
                ├── CenterDefinition（业务中心目录与能力边界）
                ├── RoleTwin（表达、规则、记忆，不授予权限）
                └── ActorContext（每次请求重新生成）

Domain Record ──> Data Product ──> Workspace / Analysis / AI / MCP / Twin
     事实             标准化视图       只读消费与受控动作
```

### 3.1 工作空间、中心和场景节点的区别

| 对象 | 作用 | 是否拥有业务事实 | 是否授予权限 | 示例 |
|---|---|---:|---:|---|
| `WorkspaceProfile` | 按岗位组织首页信息 | 否 | 否 | CEO 工作台 |
| `CenterDefinition` | 定义一个业务或平台能力域 | 是/引用所属域事实 | 否，权限仍由授权服务决定 | 运营中心、数据基础中心 |
| `SceneNode` | 3D 空间中的入口和状态投影 | 否 | 否 | 仓库、会议室、数据节点 |
| `AccessRole` | 资源、动作、字段和范围权限 | 否 | 是 | `commerce.manager` |
| `ScopeContext` | 当前集团、企业、组织、店铺和时间范围 | 否 | 限定数据范围 | 某子公司下的 4 个店铺 |
| `RoleTwin` | 分身规则、表达、记忆和模型配置 | 否 | 否 | 运营负责人分身 |

## 4. 目标产品导航

完整架构可以有多个中心，但前端不应把所有中心平铺成二十多个一级 Tab。建议使用五组导航，并由服务端根据主体权限投影。

```text
企业空间
├── 数字孪生
├── 我的工作台
└── 决策与会议

业务运营
├── 渠道与店铺
├── 商品与产品
├── 内容与设计
├── 营销增长
├── 交易
├── 客户与服务
├── 履约与仓储
├── 采购与供应链
└── 合作伙伴

经营治理
├── 经营洞察
├── 财务与结算
├── 组织与绩效
├── 流程与协同
└── 风险、质量与合规

数字底座
├── 数据基础
├── 数据产品
├── 知识中心
├── AI 与自动化
└── 集成与连接

平台管理
└── 身份、权限与平台运维
```

建议路由：

| 路由 | 责任 |
|---|---|
| `/console` | 数字孪生默认首页 |
| `/console/spatial` | 数字孪生兼容入口 |
| `/console/workspaces/{workspace_key}` | 岗位工作台 |
| `/console/decisions` | 决策、会议、行动项 |
| `/console/commerce/*` | 业务运营中心集合 |
| `/console/insights/*` | 经营洞察与驾驶舱 |
| `/console/finance/*` | 财务与结算 |
| `/console/people/*` | 组织、制度、KPI 和绩效 |
| `/console/data/foundation/*` | 数据基础维护 |
| `/console/data/products/*` | 经营事实、实体 360 和指标服务 |
| `/console/knowledge/*` | 知识资产、版本和记忆治理 |
| `/console/ai/*` | 分身、Runtime、MCP、评测和自动化 |
| `/console/integrations/*` | 第三方连接器、授权、映射和同步通道 |
| `/console/admin/*` | 平台管理与权限控制面 |

旧路由如 `/console/data/facts` 可以提供兼容跳转，但新页面不能继续让技术数据维护和业务数据应用共用一个导航层级。

## 5. 中心域完整目录

以下是面向电商公司的完整逻辑中心。它们不要求在首期全部开发，但名称、责任和数据边界现在就应该固定。

| 中心域 | 主要职责 | 主要使用者 | 主要记录或边界 |
|---|---|---|---|
| 数字孪生 | 企业空间、数据流、园区、仓库、会议室和全局状态 | 全员，按权限裁剪 | 只读空间节点、状态投影和下钻入口 |
| 岗位工作台 | 岗位指标、异常、待办、快捷操作和分身入口 | 各岗位 | 只生成聚合读模型，不拥有业务真值 |
| 决策与会议 | 议题、会议、分身讨论、决策包、行动项和复盘 | CEO、经理、专家 | 会议状态、证据快照、审批和行动提案 |
| 渠道与店铺 | 平台渠道、店铺授权、店铺配置和健康状态 | 运营、渠道负责人 | 渠道、店铺、平台规则和连接状态 |
| 商品与产品 | SPU/SKU、类目、属性、价格、生命周期和产品规划 | 产品、商品、运营 | 商品主数据、版本、定价和生命周期 |
| 内容与设计 | 图片、详情页、视频、直播素材、文案和设计任务 | 设计、内容、运营 | 内容资产、版本、审核和交付 |
| 营销增长 | 活动、优惠、广告、直播、会员、投放和归因 | 市场、运营、CEO | 活动、投放、预算、转化和 ROI |
| 交易 | 订单、支付、退款、取消、售后交易和状态 | 运营、客服、财务 | 交易状态与金额真值，不重复造订单表 |
| 客户与服务 | CRM、会员、客户 360、会话、工单、售后和投诉 | 客服、运营、管理层 | 客户主档、触点、服务记录和工单 |
| 履约与仓储 | 库存、库位、入出库、拣货、发货、物流和盘点 | 仓储、运营、客服 | 库存和履约状态、仓库和物流记录 |
| 采购与供应链 | 供应商、采购、补货、安全库存、生产和到货 | 采购、仓储、财务 | 供应商、采购单、供应周期和补货计划 |
| 合作伙伴 | 代运营商、物流商、设计外包和外部协作 | 管理层、采购、平台 | 合同、服务范围、结算和合作绩效 |
| 经营洞察 | 经营事实、趋势、异常、驾驶舱和跨域分析 | CEO、经理、财务、运营 | 消费数据产品，不直接读取源系统字段 |
| 财务与结算 | 收入、成本、毛利、平台结算、对账、发票和现金流 | 财务、CEO | 财务事实、结算批次和对账差异 |
| 组织与绩效 | 组织、岗位、制度、KPI、OKR、绩效周期和复盘 | 人力、经理、CEO | 组织业务记录和绩效事实 |
| 流程与协同 | 工作项、审批、项目、会议行动和跨部门协作 | 全员，按权限 | 状态机、责任人、截止日期和行动结果 |
| 风险、质量与合规 | 商品、交易、平台、供应链、权限和数据质量风险 | 管理层、运营、数据、平台 | 风险事件、整改、检查和合规证据 |
| 数据基础 | 来源、同步、实体模型、指标定义、质量和血缘 | 数据管理员、平台管理员 | 数据资产元数据和规范化接入记录 |
| 数据产品 | 经营事实、客户/店铺/商品 360、主题数据集和指标服务 | 分析、AI、各业务中心 | 面向消费方的标准化读模型 |
| 知识中心 | 制度、SOP、FAQ、会议纪要、聊天记录、切片和记忆候选 | 知识管理员、全员 | 知识版本、生效状态、审核和来源 |
| AI 与自动化 | 分身、Runtime、MCP、Skills、评测、AI 会议和自动化 | AI 管理员、管理层、各业务角色 | AgentRun、分身版本、工具策略和运行审计 |
| 集成与连接 | 吉客云、CRM、电商平台、飞书、微信、ERP、物流等 | 数据、平台、业务管理员 | 连接器、授权、字段映射、Webhook 和同步状态 |
| 平台管理 | 用户、权限、配置、任务、文件、审计和服务运维 | 平台管理员 | 控制面数据，不自动获得业务决策权限 |

### 5.1 “经营事实”应该放在哪里

当前数据中心中的经营事实、客户 360 和驾驶舱，不建议继续与数据源、同步任务并列。

推荐拆为：

```text
数据基础中心
├── 数据源
├── 同步批次
├── 实体模型
├── 指标定义
├── 数据质量
└── 数据血缘

数据产品 / 经营洞察中心
├── 经营事实
├── 店铺 360
├── 商品 360
├── 客户 360
├── 指标服务
├── 经营分析
└── 驾驶舱
```

经营事实是数据中心加工后的业务数据产品。它被 CEO、运营、财务、AI 和会议共同消费，不应被某个单一业务部门独占。

### 5.2 知识中心的边界

知识中心只负责知识资产生命周期：导入、清洗、切片、版本、审核、发布、退役、冲突和记忆候选。

以下动作必须留在其他中心：

- 店铺改价、上下架、投放和发券：运营/商品/营销中心；
- 客服发送、退款承诺和工单关闭：客户与服务中心；
- 制度发布、绩效确认和人员调整：组织与绩效中心；
- AI 运行、工具权限和分身评测：AI 中心。

知识中心提供被引用的证据，不直接替代业务状态机。

## 6. 多子公司和集团化架构

### 6.1 基本判断

当前系统已经要求所有核心记录携带稳定 `enterprise_id`。多子公司场景下不能把这个字段改成集团 ID，否则会破坏现有的权限、数据范围、来源映射和审计边界。

正确做法是增量增加集团层：

```text
Group（集团/控股主体，可选）
└── LegalEnterprise（法人企业，现有 enterprise_id）
    ├── BusinessUnit（事业部/品牌/区域）
    │   ├── OrgUnit（组织部门）
    │   ├── Store（店铺/渠道业务单元）
    │   └── Warehouse（仓库/履约节点）
    └── SourceSystem（该法人企业的外部系统连接）
```

首期单企业部署可以自动创建一个 `group_id` 并把当前 `enterprise_id` 挂到该集团下，业务行为不变；以后新增子公司只增加层级和成员关系，不需要重写单企业数据。

### 6.2 需要新增或扩展的核心对象

| 对象 | 作用 |
|---|---|
| `Group` | 集团级配置、集团级指标、合并口径和集团空间 |
| `EnterpriseMembership` | 一个用户可被授权到一个或多个法人企业，并可拥有不同岗位和范围 |
| `BusinessUnit` | 品牌、事业部、区域或独立经营单元 |
| `EnterpriseScopeGrant` | 对集团、法人企业、业务单元、组织、店铺和仓库的授权范围 |
| `ConsolidationProfile` | 合并范围、抵消规则、币种、汇率日期、会计期间和版本 |
| `EnterprisePolicyBinding` | 集团政策、企业政策和业务单元政策的适用范围 |
| `CenterAssignment` | 某中心在集团、企业或业务单元的启用和负责人 |
| `WorkspaceAvailability` | 当前主体在某个企业上下文中可以使用的工作空间 |
| `SourceBinding` | 外部来源与法人企业、店铺和业务单元的稳定映射 |

### 6.3 `ActorContext` 的多企业扩展

可信上下文至少要包含：

```text
group_id
current_enterprise_id
allowed_enterprise_ids
business_unit_ids
org_unit_ids
store_ids
warehouse_ids
position_ids
access_role_keys
scope_version
business_timezone
currency_context
```

客户端可以提出“切换企业”意图，但不能用 URL、请求体或自定义请求头伪造 `enterprise_id`。服务端必须检查该主体的有效成员关系、岗位、访问角色和范围，再生成新的当前上下文，并在运行、会议、分析和 MCP 会话中保存快照。

企业切换不应只是前端 Tab 切换：

1. 当前企业变化后重新请求工作空间目录、菜单和数据范围。
2. 原有页面的查询和写入请求必须失效或重新授权。
3. 切换记录、范围版本和触发的运行上下文写入审计。
4. 没有集团级权限时不能看到集团汇总或其他子公司名称。

### 6.4 多企业数据模型

所有核心事实建议采用以下字段策略：

- `group_id`：集团归属，可为空但集团部署必须填写；
- `enterprise_id`：法人企业，财务、合同、结算、来源和审计事实必须填写；
- `business_unit_id`：品牌、事业部或区域，适用于经营事实；
- `org_unit_id`：组织责任归属，适用于人员、任务和绩效；
- `store_id` / `warehouse_id`：店铺和履约范围；
- `source_system_id`、`source_record_id`：源系统映射；
- `scope_version`、`as_of`、`business_date`：授权和业务时点；
- `currency_code`、`exchange_rate_version`：金额事实的币种和换算版本。

不同类型事实的法人边界：

| 事实类型 | 必须绑定 | 可否集团汇总 |
|---|---|---:|
| 订单、退款、收款 | `enterprise_id`、店铺 | 可以，但须声明去重和币种 |
| 商品、库存、发货 | 企业、店铺或仓库 | 可以，需处理跨企业共享 SKU |
| 供应商和采购 | 法人企业、供应商 | 可以，需区分合同主体 |
| 财务收入、成本、结算 | 法人企业 | 可以，必须使用合并规则和抵消版本 |
| 人员、岗位、绩效 | 组织与任职企业 | 可以显示集团汇总，明细按范围隔离 |
| 客户主档和触点 | 数据归属企业及来源 | 可以做去重后的集团视图，但不能默认共享明细 |
| 制度和知识 | 集团、企业或业务单元 | 可以继承，但必须有生效范围和优先级 |

不能把不同法人企业的金额、库存或客户明细直接拼接成一个没有范围标签的“集团总数”。

### 6.5 指标与合并口径

集团与子公司可能存在不同的：

- 会计科目；
- 业务日期和时区；
- 币种；
- 毛利、退款和费用口径；
- 订单去重规则；
- 组织和绩效周期；
- 平台结算周期。

因此指标定义需要区分：

```text
MetricDefinition（集团基础口径）
└── EnterpriseMetricOverride（企业局部口径）
    └── BusinessUnitMetricOverride（必要时的业务单元口径）
```

返回集团指标时必须带上：

- 统计范围；
- 合并或抵消规则版本；
- 基础币种；
- 汇率日期或版本；
- 时间窗口和业务时区；
- 数据截至时间；
- 参与合并的企业列表或数量。

CEO 可以看到集团汇总，但下钻到子公司后必须重新执行子公司范围授权；财务人员可拥有某企业的明细权限，但不因此获得集团其他企业权限。

### 6.6 知识和制度的集团继承

多子公司下知识不能只使用一个全局集合。建议采用命名空间和继承关系：

```text
集团制度/知识
    ↓ 可继承
子公司制度/知识
    ↓ 可继承
业务单元/部门 SOP
```

冲突处理顺序必须显式配置：

1. 生效范围更具体的企业或业务单元版本优先；
2. 同一范围同一主题只能有一个生效版本；
3. 无法判定优先级时，不得让 AI 自行选择，应标记为制度冲突并要求人工确认；
4. AI 回答必须返回实际引用的范围、版本和生效时间。

角色记忆也应绑定 `group_id`、`enterprise_id` 或 `business_unit_id`。集团 CEO 分身可以在授权范围内做集团分析，但子公司分身不能因为共享模板而读取兄弟公司的记忆或制度细节。

### 6.7 多企业数字孪生

数字孪生可以采用两级空间：

```text
集团空间
├── 子公司 A
│   ├── 办公区
│   ├── 仓库
│   └── 数据/业务节点
├── 子公司 B
└── 集团共享数据与 AI 节点
```

场景节点必须携带稳定的 `scope_key`。进入子公司空间后，指标、人员、仓库、会议和数据流自动切换到该范围；没有权限的子公司不显示明细节点，也不通过透明建筑或悬浮标签泄露名称和状态。

三维空间只提供总览和下钻，不在集团层面直接执行跨公司写操作。跨企业变更需要进入决策、审批或平台管理流程，并明确受影响的法人企业。

### 6.8 多企业会议、AI 和 MCP

每次会议、分析运行、AI 回答和 MCP 会话都必须保存：

- 发起主体；
- 当前集团和企业上下文；
- 参与企业或业务单元范围；
- 实际授权范围与版本；
- 使用的指标、知识、记忆和合并口径版本；
- 证据快照和 `as_of`；
- 分身实例和分身配置版本。

会议范围建议分为：

- 单企业会议：只能读取该企业范围；
- 多企业比较：只允许读取明确授权的企业集合；
- 集团决策会议：可读取集团合并数据，子公司明细必须按权限和议题需要提供。

分身不会继承被模拟对象的账号权限，始终使用真实发起人的权限与当前范围交集：

```text
实际可用范围 = 发起人权限
             ∩ 当前企业/集团范围
             ∩ 分身边界
             ∩ 工具策略
             ∩ 会议或运行声明范围
```

## 7. 岗位工作台与中心的关系

岗位工作台是“问题入口”，中心是“问题处理地”。

| 岗位 | 工作台关注点 | 主要中心 |
|---|---|---|
| CEO/老板 | 集团或企业经营结果、重大异常、决策和风险 | 数字孪生、经营洞察、财务、组织绩效、决策与会议、AI |
| 子公司负责人 | 本法人企业目标、店铺、利润、人员和待决事项 | 经营洞察、渠道与店铺、财务、组织绩效、决策与会议 |
| 部门负责人 | 部门偏差、团队任务、制度和行动 | 经营洞察、流程协同、组织绩效及对应业务中心 |
| 运营负责人 | 店铺、商品、营销、客户和履约异常 | 渠道与店铺、商品、营销、客户、履约、经营洞察 |
| 店铺运营 | 今日经营问题、待办和可执行建议 | 渠道与店铺、商品、营销、经营洞察 |
| 客服负责人 | 待回复、升级、售后和制度证据 | 客户与服务、交易、知识、AI |
| 仓储/供应链 | 库存、履约、采购和补货 | 履约与仓储、采购与供应链、经营洞察 |
| 财务 | 收入、成本、结算和差异 | 财务与结算、交易、经营洞察 |
| 人力/制度负责人 | 制度、岗位、KPI、绩效和组织执行 | 组织与绩效、知识、流程协同 |
| 数据管理员 | 连接、同步、质量、指标和血缘 | 数据基础、数据产品、集成与连接 |
| AI/平台管理员 | Provider、Runtime、MCP、任务和审计 | AI、平台管理、数据基础、集成与连接 |

工作台可根据当前企业上下文显示不同指标，但不会因切换到“集团工作台”而自动获得集团权限。

## 8. 权限与菜单模型

权限至少分为五层：

1. **体验层**：是否显示数字孪生、工作台或某个中心入口；
2. **中心层**：是否可以进入渠道、交易、数据基础、知识或 AI 中心；
3. **功能层**：查看、创建、编辑、审批、发布、重试或执行；
4. **数据范围层**：集团、法人企业、业务单元、部门、店铺、仓库或客户范围；
5. **字段和动作层**：金额、客户敏感信息、外部写入、批量操作和跨企业合并。

菜单只是以上授权结果的投影。工作空间、分身名称、3D 建筑点击和 URL 都不能替代后端授权。

多企业角色建议使用组合，而不是只定义一个“集团管理员”：

- `group.executive`：集团经营汇总和决策；
- `enterprise.admin`：某法人企业的平台和组织管理；
- `business.manager`：某事业部或品牌经营管理；
- `store.operator`：指定店铺运营；
- `finance.controller`：指定企业财务和结算；
- `data.governor`：数据基础和数据产品治理；
- `ai.operator`：AI 运行、分身、MCP 和评测治理；
- `platform.operator`：跨企业平台运维，但不默认获得业务明细。

一个账号可以拥有多个企业成员关系和多个访问角色，但每次请求只使用当前有效上下文和权限交集。岗位、访问角色、工作台和分身仍然保持独立。

## 9. 数据、API 和事件边界

### 9.1 领域数据流

```text
第三方系统
  ↓ 连接器与来源映射
数据基础中心
  ↓ 规范实体、事实、指标和质量事件
数据产品中心
  ↓ 受控读模型/API
业务中心、经营洞察、工作台、AI、MCP、数字孪生
```

业务中心需要写入时，必须写入自己的领域 API；不能通过 MCP、数据中心或工作台直接改写原始事实。

### 9.2 共享字段

所有跨中心的事件和读模型至少考虑：

```text
group_id
enterprise_id
business_unit_id
org_unit_id
store_id / warehouse_id
scope_version
business_date
as_of
source_system_id
source_record_id
request_id
run_id
```

### 9.3 中心目录配置化

建议新增版本化 `CenterDefinition`，至少包含：

- `center_key`、显示名称和版本；
- 所属导航组；
- 默认路由和子路由；
- 能力键与依赖的数据产品；
- 可见岗位和最低访问角色；
- 数据范围级别；
- 3D 场景节点键；
- 工作台可引用的指标、提醒和快捷动作；
- 是否在某集团、企业或业务单元启用。

前端不应继续维护大量 `if (role === ...)` 或手工隐藏菜单；菜单和工作台均应消费服务端目录投影。

## 10. 实施顺序

完整设计现在固定，实际开发仍采用纵向切片，不一次性实现二十多个中心。

### 阶段 A：导航和契约收口

- 新增 `CenterDefinition` 和导航组契约；
- 新增 `ScopeContext`、`EnterpriseMembership` 和集团/企业上下文契约；
- 设计中心、工作台、数字孪生和场景节点的稳定键；
- 旧路由提供兼容重定向；
- 将 `/console` 确认为默认数字孪生首页，`/console/spatial` 作为兼容入口，将 `/console/workspaces/{key}` 作为独立工作台。

### 阶段 B：数据中心拆分

- 把当前数据中心拆成“数据基础”和“数据产品/经营洞察”；
- 数据源、同步、实体、指标、质量、血缘留在数据基础；
- 经营事实、客户 360、店铺 360、驾驶舱和分析迁到数据产品/经营洞察；
- 不复制事实表，先迁移路由和读模型；
- 对每个页面补充企业范围、数据截至时间和来源批次。

### 阶段 C：业务中心归位

- 交易、客户服务、履约、采购、营销、商品、内容和设计按领域归位；
- 知识中心移除业务执行入口；
- 决策与会议、流程协同和行动台账统一引用中心数据；
- 工作台快捷入口只指向中心对象，不在工作台复制编辑表单。

### 阶段 D：多子公司数据底座

- 增加 `group_id`，创建一个默认集团并绑定现有企业；
- 增加企业成员关系、企业范围和当前企业上下文；
- 为来源、指标、知识、会议、分析、AI 运行和 MCP 会话补充企业范围；
- 完成集团汇总、企业明细和范围隔离测试；
- 再接入真实多公司数据，不先修改第三方源字段契约。

### 阶段 E：AI、会议和数字孪生上下文

- AI、会议、分析和 MCP 使用统一 `ScopeContext`；
- 分身模板可集团级复用，但实例和记忆按企业或业务单元隔离；
- 集团空间与子公司空间使用同一场景契约和权限裁剪；
- 会议和行动明确受影响法人企业，跨企业写入继续要求分权审批。

### 阶段 F：岗位工作台重组

- 工作台首屏只保留岗位关注的指标、异常、待办和入口；
- CEO/集团工作台与子公司负责人工作台使用不同默认范围；
- 经理和员工工作台按组织与店铺范围下钻；
- 平台、数据和 AI 工作台显示控制面信息，不默认展示业务敏感明细；
- 通过服务端 Read Model 生成菜单和布局，不在前端写死岗位逻辑。

## 11. 验收标准

### 产品结构

- 登录默认进入数字孪生首页；
- 岗位工作台可以独立访问；
- 数据基础与经营洞察在导航和页面层面清晰分离；
- 知识中心没有业务执行入口；
- 每个业务中心有清晰的对象、动作和负责人；
- 工作台下钻到中心后沿用同一指标和事实口径。

### 多子公司

- 当前单企业数据迁移到一个默认集团后，原有查询和权限结果不变；
- 一个用户可以被授权多个法人企业，但切换企业会重新生成菜单、范围和工作空间；
- 子公司用户不能通过集团参数、工作空间或 AI 提问读取兄弟公司数据；
- 集团指标明确合并范围、币种、汇率、抵消规则和数据截至时间；
- 财务、客户、人员和知识的法人边界经过隔离测试；
- 集团会议只能使用明确声明且实际授权的企业集合。

### 技术与体验

- API、Web、渠道、Agent、MCP 和 Worker 使用同一 `ActorContext` 与 `ScopeContext`；
- 工作台切换不改变主体权限和数据范围；
- 3D 节点与二维页面使用稳定中心键和业务键；
- 数字孪生无 WebGL 时存在等价二维入口；
- 页面无解释性旁白，桌面、超宽屏和移动端无重叠和不可见关键操作；
- 新增中心、企业和工作台有契约测试、权限测试和路由验收路径。

## 12. 明确不做的事情

- 不因为中心数量增加就提前拆成微服务；
- 不为每个岗位复制一套数据库、指标或知识库；
- 不让“集团管理员”默认读取全部客户和财务明细；
- 不让分身继承被模拟人员的账号权限；
- 不用前端隐藏菜单代替服务端授权；
- 不把经营事实、客户 360 和驾驶舱继续堆进数据源维护页；
- 不把所有业务操作塞进知识中心或 AI 中心；
- 不在 3D 场景中直接执行不可逆的外部写操作；
- 不为追求“完整菜单”而在首期实现没有真实数据和验收路径的中心。

# 岗位工作空间与角色化信息架构改造指南

- 文档编号：DX-007
- 版本：0.1
- 状态：开发指导稿
- 适用产品：知行数枢 · 企业数据智能运营中枢
- 编写日期：2026-09-02
- 关联任务：`UIA-001`、`UIA-002`、`UIA-004`、`UIA-007`、`UIA-008`、`IAM-003`、`TWI-001`

> 本指南用于指导后续开发。它对现有产品蓝图中“角色首页、导航投影和工作台”的细节进行补充；若与旧版页面草图冲突，以本指南的岗位工作空间模型为准。它不替换身份、权限、数据中心、RoleTwin 或既有领域契约。

> 中心域、一级导航、数字孪生默认入口以及集团/子公司边界以 `docs/development/08-enterprise-center-domain-and-workspace-boundary-guide.md`（DX-008）为准；本指南只继续约束岗位工作空间的投影和运行上下文，不再定义业务中心的归属。

## 1. 结论与改造判断

按岗位和职责呈现不同的首页与重点模块是正确且必要的。企业数据中心面向所有业务，但不同人员进入系统时关心的问题不同：CEO 关注经营结果和需要拍板的事项，部门经理关注偏差和团队行动，运营员工关注今天要做什么，平台管理员关注链路和系统健康。让所有人看到同一套底层菜单，会造成信息过载，也会削弱数据中心的价值感。

需要修正的一点是：不能把“岗位”“权限”“页面首页”当成同一个角色字段。正确的关系是：

```text
岗位 Position ─┐
访问角色 AccessRole ─┼─> 服务端授权 ActorContext ─> 可用数据与动作
数据范围 ScopeGrant ─┘

Position + 当前职责 + 授权范围 + 可选工作模式
        └─> WorkspaceProfile（岗位工作空间配置）

WorkspaceProfile + 当前任务上下文 ─> 首页 Read Model
RoleTwin 仅负责表达与分析能力，不授予任何访问权限
```

因此产品采用“一套平台、多个工作空间、统一能力中心”的结构：

1. 业务数据、指标、知识、记忆、运行、行动仍只有一套真值和契约。
2. 每个岗位有一个默认工作空间，首页只投影该岗位最需要的指标、异常、待办和入口。
3. 侧栏和按钮是授权结果的投影，后端授权检查仍然是最终边界。
4. 用户可以在本人被授权的多个职责工作空间之间切换，但不能通过切换器伪造岗位、角色或数据范围。
5. 3D 数字孪生是工作空间的空间化视图，不是另一套业务系统；没有 WebGL 或不适合沉浸式操作时，必须提供等价二维视图。

## 2. 改造目标与非目标

### 2.1 目标

- 登录后首先看到“我的工作台”，并根据服务端返回的工作空间配置呈现内容。
- CEO、部门经理、运营员工、客服、财务、数据治理、平台运维和 AI 运维各自有明确的信息优先级。
- 同一指标在不同工作空间中保持相同口径、时间和数据来源，只改变展示重点和下钻入口。
- 首页上的异常、决策、任务和行动可以下钻到现有中心，而不是复制一份新业务逻辑。
- AI 回答、数字会议和后续受控动作都携带当前岗位、主体和数据范围上下文。
- 通过可版本化配置增加新岗位，不再在前端大量写 `if (role === ...)`。
- 桌面、超宽屏和移动视口均保持可扫描、无重叠、无不可见关键操作。

### 2.2 非目标

- 不为每个岗位复制一套数据表、指标计算或知识库。
- 不用 `WorkspaceProfile` 替代 `AccessRole`、`ScopeGrant` 或 API 授权。
- 不允许 CEO 工作空间绕过敏感数据、审批或行动权限。
- 不把所有页面强行改成 3D，也不在 3D 场景中直接执行不可逆外部写操作。
- 不以职位名称字符串作为唯一授权依据；一个人可以兼任多个岗位。
- 不在界面加入架构介绍、教程、演示旁白或解释页面本身的说明性文字。
- 不把岗位首页做成营销大屏；高频操作仍使用安静、密集的后台工作台。

## 3. 用户与工作空间分层

### 3.1 领域对象边界

| 对象 | 责任 | 是否授予权限 | 典型示例 |
|---|---|---:|---|
| `Principal` / `UserAccount` | 登录主体、账号状态、渠道绑定 | 否 | 张三的本地账号 |
| `Enterprise` | 企业边界 | 否 | 知行电商 |
| `OrgUnit` | 组织层级 | 否 | 运营中心、客服中心 |
| `Position` | 岗位、职责、任职关系 | 否 | 运营经理、财务负责人 |
| `AccessRole` | 资源、动作和数据范围权限集合 | 是 | `commerce.manager` |
| `ScopeGrant` | 企业、组织、店铺等数据范围 | 是 | 运营中心下 4 个店铺 |
| `WorkspaceProfile` | 首页、导航、指标组、待办和空间视图配置 | 否 | `manager-operations` |
| `RoleTwin` | 岗位规则、个人表达、记忆和模型配置 | 否 | 运营负责人分身 |
| `WorkspaceSession` | 本次进入的工作空间和筛选上下文 | 否 | CEO 当前查看本月全企业 |

### 3.2 工作空间解析规则

服务端按以下顺序解析工作空间：

1. 从可信会话或渠道身份解析 `ActorContext`。
2. 读取当前企业、有效账号、组织、任职、访问角色和数据范围。
3. 根据任职关系与配置匹配一个或多个可用 `WorkspaceProfile`。
4. 对工作空间中的模块、指标、提醒和快捷动作再次执行权限与范围过滤。
5. 生成版本化的 `WorkspaceReadModel` 返回 Web、飞书卡片和后续 Agent 使用。
6. 若用户没有配置专属工作空间，回退到权限允许的“通用工作台”，不能回退到企业全域。

客户端可以提交 `workspace_key` 作为选择意图，但服务端必须验证该工作空间属于当前主体，且其中每一项数据和动作取当前授权结果与工作空间上限的交集。客户端不得提交 `principal_id`、角色、企业或店铺编码来改变上下文。

### 3.3 多岗位与临时职责

- 同一账号可有主岗位和兼职岗位，默认工作空间来自主岗位。
- 用户可在工作空间切换器中选择当前有效兼职职责；切换记录写入审计上下文。
- 临时委托只能产生委托人权限和范围的子集，不能自动获得被委托人的全部首页。
- 组织、岗位或访问角色失效后，下一次读取工作空间立即重新解析；旧运行仍保存当时的快照。
- RoleTwin 选择遵循“调用者权限 ∩ 分身边界 ∩ 工具策略”，不能因进入某个工作空间扩大权限。

## 4. 目标产品结构

### 4.1 统一壳与工作空间层

登录后的统一壳保持以下固定区域：

- 顶栏：企业、业务日期、数据截至时间、全局搜索、企业助手、通知和账号菜单。
- 工作空间栏：当前工作空间名称、数据范围、切换入口和刷新时间。
- 主区：角色化指标、异常/待办、最近活动和下一步动作。
- 二级导航：只展示当前主体已授权且与当前工作空间相关的中心入口。
- 右侧/底部详情：证据、来源、版本、权限解释和操作确认。

“工作台”是进入系统后的业务首页；“企业数据中心、知识中心、分身中心、会议中心、智能分析中心、行动中心、客服工作台、平台管理”仍是共享能力中心。工作空间首页引用这些中心，不在首页重新实现业务功能。

### 4.2 面向岗位的工作空间目录

以下是首批正式配置。岗位名称只是默认匹配条件，最终显示和数据范围由服务端授权决定。

| 工作空间键 | 适用对象 | 默认路由 | 首屏问题 | 默认范围 |
|---|---|---|---|---|
| `executive` | CEO、老板、经营决策人 | `/console/workspaces/executive` | 企业现在发生了什么，需要我决定什么？ | 企业全域或授权企业集合 |
| `manager` | 部门负责人、区域负责人 | `/console/workspaces/manager` | 部门哪里偏离目标，谁需要行动？ | 本组织子树及授权店铺 |
| `operator` | 店长、运营专员、商品/广告运营 | `/console/workspaces/operator` | 今天要处理哪些店铺经营问题？ | 本人负责的店铺/业务单元 |
| `service` | 客服主管、客服员工 | `/console/workspaces/service` | 哪些会话需回复、升级或核验？ | 授权客服队列与关联订单 |
| `finance` | 财务负责人、结算人员 | `/console/workspaces/finance` | 收入、成本、退款和预算是否可对账？ | 企业或授权组织财务范围 |
| `people` | 人力、绩效、制度负责人 | `/console/workspaces/people` | 制度、KPI 和人员执行是否一致？ | 组织、岗位和已授权人员 |
| `data-governance` | 数据管理员、数据产品负责人 | `/console/workspaces/data-governance` | 数据是否完整、及时、可解释？ | 企业数据资产与质量范围 |
| `platform-ops` | 平台管理员、系统运维 | `/console/workspaces/platform-ops` | 平台、任务、权限和渠道是否健康？ | 平台控制面，不自动获得业务决策权 |
| `ai-ops` | AI 平台管理员、评测负责人 | `/console/workspaces/ai-ops` | 模型、工具、分身和运行质量是否可控？ | AI 运行、评测和工具治理资产 |

首期实现顺序为 `executive`、`manager`、`operator`、`platform-ops`，随后接入 `service`、`finance`、`data-governance`；`people` 和 `ai-ops` 可以先作为 `platform-ops` 的子视图，待数据与评测任务成熟后独立。

## 5. 各工作空间的功能设计

### 5.1 CEO 决策工作空间

用户进入后先看到经营结果和需要拍板的事项，不先显示数据库技术状态。

首屏模块：

1. 企业关键指标：GMV、毛利、订单、退款率、广告 ROI、库存健康度；每项显示口径、范围、`as_of` 和相对比较。
2. 经营异常：按影响金额、影响范围和持续时间排序，可进入店铺诊断。
3. 待决策事项：会议决策包、预算、重大风险和待确认行动。
4. 经营简报：最近日报/周报及与上期差异。
5. 组织与店铺贡献：只显示获授权的汇总和可下钻节点。
6. AI 决策入口：使用 CEO 分身生成事实、推断、风险、选项和未知项。
7. 数字空间入口：企业园区总览、会议室和关键经营节点；3D 是可选视图。

快捷动作：查看异常、追问指标、发起数字会议、确认决策包、查看行动结果。

不在默认首页显示：原始同步日志、Provider 探针、权限配置、文件交换明细。若 CEO 同时有平台权限，可通过授权菜单进入，不因首页隐藏而撤销权限。

决策链路必须是：

```text
指标变化 → 异常识别 → 证据/口径 → AI 分析 → 多角色会议
→ 人工确认 → 行动提议 → 分权审批 → 结果与复盘
```

### 5.2 部门经理工作空间

首屏模块：

1. 部门目标与实际：销售、毛利、转化、广告、库存或部门自定义 KPI。
2. 偏差排行：按店铺、团队、岗位和时间窗口下钻。
3. 待处理队列：行动审批、异常复核、员工反馈和制度确认。
4. 团队执行：本人组织子树的工作项、负责人、截止日期和阻塞原因。
5. 制度与 KPI 更新：仅展示与本部门生效的制度版本和待确认变化。
6. 部门分身入口：岗位指导、诊断复盘和会议邀请。

快捷动作：店铺诊断、分派工作、审批行动、发起部门议题、查看指标口径。

经理可以查看部门范围，不可通过工作空间参数读取其他部门；跨部门会议使用范围交集或经授权的企业范围。

### 5.3 店铺运营工作空间

首屏模块：

1. 今日经营：订单、销售额、转化、广告花费、ROI、库存告警。
2. 待办清单：按优先级、停止条件和证据链接排序。
3. 店铺异常：价格、流量、广告、库存、履约和售后问题。
4. 商品/SKU 机会：只读建议和影响估计，不直接改价、上架或投放。
5. 运营助手：基于当前店铺范围回答“为什么”和“下一步做什么”。
6. 最近工作结果：本人承接的行动和结果证据。

快捷动作：刷新店铺数据、创建内部工作项、提交诊断、反馈数据问题。自动改价、自动投放、自动发券等外部写入默认不开放。

### 5.4 客服工作空间

首屏模块：

1. 待回复会话、响应时长和超时风险。
2. 高风险队列：金额、退款、承诺、投诉和字段对账冲突。
3. 当前会话的订单、物流、商品和售后只读上下文。
4. AI 回复草稿、制度证据和风险门禁。
5. 转人工与接管工单。
6. 处理质量：草稿采纳、修改、转人工和解决时长。

客服工作空间不复制交易事实；订单、退款和客户资料继续从数据中心规范事实与客户 360 投影读取。草稿必须人工确认，真实渠道发送另行经过渠道权限和动作审批。

### 5.5 财务工作空间

首屏模块：

1. 收入、成本、毛利、退款、平台费用和现金/结算差异。
2. 对账队列：源系统差异、缺失批次、重复记录和异常金额。
3. 预算执行与广告投放回报。
4. 待审批行动和影响金额。
5. 月/周结简报与证据快照。
6. 财务分身的解释和复核入口。

财务视角可以拥有更细的金额和成本权限，但不得用“财务岗位”自动取得系统管理员权限；数据范围和字段级敏感策略由授权服务决定。

### 5.6 人员、制度与绩效工作空间

首屏模块：

1. 制度版本及生效状态。
2. KPI 目标、完成度和异常人员/组织。
3. 待审核记忆、反馈和制度冲突。
4. 岗位模板、能力边界和培训/指导任务。
5. 绩效会议议题与行动跟踪。

该空间管理“规则和执行状态”，不把聊天原文直接当成制度，也不允许 AI 自动发布制度。发布、退役和绩效口径变更仍走现有知识生命周期和人工确认。

### 5.7 数据治理工作空间

首屏模块：

1. 数据源连接状态、最近同步批次和延迟。
2. 规范经营事实覆盖率与各事实族对账。
3. 实体映射、来源 ID 和映射版本。
4. 指标目录、负责人和口径变更。
5. 质量规则、缺失、冲突、重复和范围不符。
6. 数据血缘和待处理质量事件。

数据治理工作空间可以看到经营资产的技术状态，但不因数据管理员身份自动获得所有业务金额或客户隐私字段；显示内容仍取决于字段和范围授权。

### 5.8 平台运维工作空间

首屏模块：

1. 账号、组织、访问角色和委托变化。
2. 后台任务、失败 Attempt、重试和 Worker 健康。
3. 工具注册、MCP 会话和调用审计。
4. 渠道身份绑定、通知投递和未读状态。
5. 文件资产、批量交换和参数字典。
6. 统一审计检索、权限解释和平台配置变更。

平台管理员的默认首页不显示 CEO 经营决策结论，只显示平台运行事实；若另有业务访问角色，才出现对应业务工作空间。

### 5.9 AI 运维工作空间

首屏模块：

1. Provider、模型、延迟、错误率、Token 和成本趋势。
2. 分身版本、发布状态、真实运行和回退原因。
3. 记忆与知识供应商评测：Recall@3、MRR、延迟、失败。
4. MCP 工具风险、允许范围和调用结果。
5. 评测套件、基线差异和人工反馈候选。
6. AI 运行异常与待处理治理项。

AI 运维可以管理运行配置，但不能修改经营事实、制度生效状态或绕过行动审批。

## 6. 导航与模块投影

### 6.1 导航原则

导航由三部分合成：

```text
最终导航 = 当前主体权限允许的中心
         ∩ 工作空间允许的中心
         ∩ 当前部署启用的模块
```

现有 `apps/web/src/lib/navigation.ts` 继续作为稳定模块目录，但不再承担所有岗位首页逻辑。后续应将导航元数据拆为：

- `center_key`：数据、知识、分身、会议、分析、行动、客服、平台。
- `module_key`：某个中心中的具体页面。
- `required_permissions`：访问该模块的资源/动作权限。
- `workspace_visibility`：默认在哪些工作空间出现。
- `default_rank`：同一空间中的排序。
- `delivery_state`：`prototype`、`implemented`、`unavailable`。

页面可以被多个工作空间引用，但路由和业务服务只有一份。工作空间首页的“经营异常”链接到分析中心，“待审批行动”链接到行动中心，“数据延迟”链接到数据质量页。

### 6.2 首页模块类型

首页只允许使用可复用的业务模块类型：

- `MetricStrip`：指标数值、比较、口径、数据时间。
- `AttentionQueue`：异常、风险、待办、优先级和状态。
- `DecisionQueue`：待确认决策包、审批和影响。
- `WorkQueue`：本人或组织范围内的工作项。
- `EvidencePanel`：来源、版本、批次、快照和下钻。
- `ActivityTimeline`：会议、行动、同步或制度活动。
- `AssistantEntry`：当前空间与范围预填充的问答入口。
- `SceneEntry`：可选的 3D 空间入口和对象计数。
- `FreshnessBadge`：数据截至时间、延迟和部分失败状态。

禁止为单个岗位继续创建不可复用的“专属大卡片”组件，除非它对应一个稳定业务对象或动作契约。

## 7. 数据与 API 改造设计

### 7.1 `WorkspaceProfile` 最小契约

建议新增自有契约（可先作为 Python/TypeScript 类型，稳定后再建立 JSON Schema）：

```json
{
  "schema_version": 1,
  "key": "executive",
  "label": "企业决策中心",
  "audience": ["executive"],
  "default_route": "/console/workspaces/executive",
  "navigation_keys": ["home", "cockpit", "data", "analysis", "meetings", "actions"],
  "metric_keys": ["gmv", "gross_margin", "orders", "refund_rate", "ad_roi", "inventory_health"],
  "attention_query_keys": ["commerce_anomalies", "decision_pending", "action_pending"],
  "quick_action_keys": ["ask_analysis", "start_meeting", "review_decision"],
  "scene_key": "enterprise-campus",
  "layout_version": 1,
  "delivery_state": "implemented"
}
```

契约要求：

- `key` 稳定且不可用中文标题作为主键。
- 配置只描述投影，不保存用户权限和企业业务事实。
- 指标、队列和快捷动作引用领域查询键，不内嵌 SQL 或源系统字段。
- `layout_version` 便于桌面、移动和超宽屏逐步升级。
- `delivery_state` 明确能力是原型、已实现还是暂不可用。

### 7.2 `WorkspaceReadModel` 返回结构

建议新增以下接口：

| 方法 | 路径 | 作用 |
|---|---|---|
| `GET` | `/api/v1/workspaces/me` | 返回当前主体可用工作空间、默认空间、范围摘要和导航投影 |
| `GET` | `/api/v1/workspaces/{workspace_key}` | 返回指定工作空间的元数据和可用模块，服务端再次授权 |
| `GET` | `/api/v1/workspaces/{workspace_key}/read-model` | 返回首页指标、异常、待办、活动、证据和空间状态 |
| `POST` | `/api/v1/workspaces/{workspace_key}/refresh` | 触发受控刷新或重新读取，不创建业务写入 |

返回模型建议包含：

```text
schema_version
workspace { key, label, position_keys, layout_version }
actor { principal_ref, org_ref, position_refs }
scope { kind, keys, label, as_of }
navigation[]
metrics[]
attention[]
decisions[]
work_items[]
activities[]
freshness[]
quick_actions[]
scene { scene_key, object_refs, layer_keys }
generated_at
request_id
```

每个业务数值必须携带 `metric_key`、定义版本、单位、时间范围、`as_of`、来源/批次摘要和必要的 `evidence_keys`。AI 摘要必须区分事实、推断、建议和未知，不能用工作空间标题替代证据。

### 7.3 读取和缓存规则

- 首期从现有领域服务组合 Read Model，不在前端拼接多个不一致接口。
- 可以使用短时缓存，但缓存键至少包含企业、主体授权版本、工作空间键、范围和业务日期。
- 权限、范围、账号状态或岗位变化后，下一次读取必须失效旧投影。
- 读模型失败时返回局部可用模块和明确错误状态，不用静态假数据补齐。
- 3D 场景和普通后台引用同一 `object_ref`，便于点击对象后跳转二维详情。

## 8. AI、数字会议与岗位工作空间的结合

### 8.1 AI 上下文

每次助手、分身、分析和会议运行都应接收：

- 可信 `ActorContext`。
- 当前 `workspace_key` 和用户主动选择的任务模式。
- 服务端解析后的数据范围和业务时间。
- 当前指标/知识/记忆版本。
- 角色分身版本与能力边界。
- 工具白名单、只读/写入标识和风险级别。

工作空间只帮助 AI 理解用户当前任务，不改变权限。比如 CEO 工作空间的“广告 ROI 异常”可以预填充问题和证据，但仍需按当前主体的经营查询权限读取。

### 8.2 多分身议题室

任何具备会议发起权限的工作空间都可以发起议题。会议流程统一为：

1. 从工作空间携带议题、范围和业务日期。
2. 服务端冻结指标、事实、制度和分身版本。
3. 各角色分身独立分析，再进行交叉质询和反方审查。
4. 输出共识、分歧、风险、行动项和复盘日期。
5. 行动项进入统一提案、审批和内部工作状态机。

会议参与者不能因为来自 CEO、财务或运营工作空间而自动读取更大范围；每个席位的观点使用同一个会议证据快照和其被允许的字段。

### 8.3 岗位化 AI 输出

同一经营事实在不同工作空间的输出重点不同，但事实不可变：

| 空间 | AI 输出优先级 |
|---|---|
| CEO | 影响、原因、决策选项、风险、需确认事项 |
| 经理 | 偏差、责任范围、行动建议、负责人和截止时间 |
| 运营 | 今日任务、操作步骤、停止条件、证据链接 |
| 客服 | 可发送草稿、制度依据、风险门禁、转人工原因 |
| 财务 | 对账差异、金额影响、期间口径、复核项 |
| 数据治理 | 来源、血缘、质量、延迟、修复任务 |
| 平台/AI 运维 | 状态、错误、运行、权限、版本和重试 |

## 9. 3D 数字孪生落地边界

### 9.1 适合的使用方式

- CEO：企业园区、关键经营节点、数字会议室和决策流动。
- 经理：部门空间、店铺群组、异常热区和任务路线。
- 运营：店铺/仓储空间、商品或库存热点、待办对象。
- 平台/数据管理员：数据源、同步任务、质量告警和 AI 运行节点。
- 会议：角色分身到场、议题阶段、共识/分歧状态和证据线路。

### 9.2 不能让 3D 承担的责任

- 不在 Canvas 中维护另一套权限、指标或状态真值。
- 不把复杂表格、权限批量配置、字段映射强塞进空间场景。
- 不让点击建筑或人物直接触发外部写操作；先进入二维详情或受控操作面板。
- 不以镜头动画掩盖数据加载、失败或权限拒绝。

### 9.3 技术与体验要求

- Three.js 作为渐进增强；WebGL 不可用时显示同一 Read Model 的二维列表/图表。
- 建筑、人物、会议室和线路对象都使用稳定业务键。
- 选中、悬停、双击、拖拽旋转、平移、缩放和复位行为统一，并提供键盘/触控替代。
- 场景按岗位只加载必要对象和图层，避免 CEO 看到仓库每个 SKU 的全部几何体。
- 关键文本使用 HTML overlay 或可读标签，不依赖远景 Canvas 小字。
- 首屏必须先显示指标和状态，再异步加载高质量模型；模型失败不影响后台使用。
- 3D 场景中的“进入数据详情”使用 `object_ref` 跳转现有中心，返回后保留工作空间和筛选上下文。

- “这里是某模块的介绍”“用于展示……”“架构说明”“数据链路说明”。

能力未实现时用统一状态标签 `prototype`、`unavailable` 或错误状态表达，不用说明性段落补偿。

## 11. 后端与契约改造清单

### 11.1 服务层

建议新增：

- `services/api/src/zhixing_api/workspace_service.py`：工作空间解析、配置和读模型编排。
- `services/api/src/zhixing_api/workspace_schemas.py`：请求/响应模型与版本校验。
- `services/api/src/zhixing_api/routers/workspaces.py`：工作空间读取接口。
- `services/api/src/zhixing_api/workspace_seed.py`：开发环境的工作空间配置种子，不写入真实权限。

复用而不重建：

- `actor_context.py`、`identity_service.py`、`identity_management_service.py`：主体与授权。
- `data_center_service.py`、`analysis_service.py`、`customer_360_service.py`：经营读模型。
- `knowledge_service.py`、`memory_service.py`、`role_twin_service.py`：知识、记忆与分身。
- `decision_service.py`、`action_service.py`、`ai_operations_service.py`：会议、行动和运行。

### 11.2 数据库策略

首期可以将工作空间目录作为版本化配置文件或数据库种子，不急于建复杂的可视化布局编辑器。确定需要企业自定义后再增加：

- `workspace_profile`：工作空间元数据和版本。
- `workspace_module_projection`：模块、排序和可见性。
- `workspace_metric_binding`：指标查询键和展示规则。
- `workspace_attention_binding`：异常/待办查询键和优先级。
- `workspace_quick_action`：动作键和前置权限。
- `workspace_layout`：桌面、移动、超宽屏布局版本。

这些表必须带 `enterprise_id`、状态、版本和更新时间；不能把权限集合、源系统字段或指标公式复制进去。

### 11.3 API 一致性

- Web、飞书卡片、Agent 和 MCP 使用同一工作空间解析结果，但不同渠道可以使用不同的展示布局。
- 工作空间 API 的 401/403、请求 ID、运行 ID 和错误 Envelope 与现有接口一致。
- 所有写动作仍进入 ActionProposal、审批和执行台账；工作空间只提供入口。
- 指标查询、证据和 AI 运行必须记录 `workspace_key` 作为上下文字段，便于复盘“用户从哪个岗位视角发起”。

## 12. 分阶段实施计划

### 阶段 A：契约与目录（P0）

- 建立 `WorkspaceProfile`、`WorkspaceReadModel` 和模块投影类型。
- 盘点现有中心、页面、权限、指标和状态，形成唯一模块注册表。
- 将 CEO、经理、运营、平台运维四个工作空间配置成服务端可读目录。
- 增加解析规则、无工作空间回退和多岗位切换测试。

完成标准：不改业务事实表即可从数据库/API 返回当前主体的默认工作空间、模块和范围摘要。

### 阶段 B：首页读模型（P0）

- 实现 `/workspaces/me` 与 `/workspaces/{key}/read-model`。
- 将现有 `/console` 改为工作空间首页，首屏读取真实数据库数据。
- CEO 和经理先接入指标、异常、决策、行动、活动和证据下钻。
- 运营接入店铺待办和工作项；平台运维接入任务、权限和审计状态。

完成标准：四种主体登录后首页不同，但点入同一个中心时使用同一业务对象、同一指标口径和同一权限结果。

### 阶段 C：导航与交互收口（P0）

- 侧栏、二级导航、面包屑和全局搜索按工作空间与权限交集投影。
- 工作空间切换器只显示服务端允许项，切换后保留企业和时间筛选。
- 统一加载、空数据、部分失败、无权限、过期和重试状态。
- 优先将新增、编辑、审批、停用、重试收口到 Dialog/Drawer/ConfirmDialog/Toast。
- 清理页面中的架构、演示和教程式文案。

完成标准：1440×900、2515×1199、390×844 下无横向溢出、文字重叠和关键操作丢失。

### 阶段 D：AI 与会议上下文（P1）

- 助手、分身问数、店铺诊断和数字会议携带 `workspace_key` 与范围摘要。
- 根据工作空间提供不同输出模板，但事实、证据、记忆和权限不变。
- 将“从异常发起会议、从决策生成行动”串成可回放故事。
- 增加跨岗位信息泄漏和 RoleTwin 权限提升评测。

完成标准：同一问题从 CEO、经理和运营工作空间得到不同重点，但不会出现超出各自范围的事实。

### 阶段 E：3D 工作空间视图（P1）

- 企业、部门、店铺和平台场景使用同一对象键与工作空间配置。
- 选择对象后显示上下文操作，双击进入二维详情；二维页面可以返回原场景。
- 会议室显示参与分身到场、阶段和决策流，但不把动画当成状态真值。
- 实施 WebGL 降级、按视距加载、对象选中和触控/键盘替代。

完成标准：3D 不可用时全部核心数据和操作仍可完成，场景只改变观察方式。

### 阶段 F：扩展岗位与企业配置（P2）

- 增加客服、财务、数据治理、人员/制度和 AI 运维的独立工作空间。
- 允许企业管理员从受治理目录选择模块、指标组和默认布局。
- 增加工作空间配置版本、审批和回滚；企业自定义不改变领域权限。

完成标准：新增一个工作空间只需要新增配置和少量读模型适配，不复制整套页面和数据库。

## 13. 测试与验收

### 13.1 后端测试

- 不同 `Position`、`AccessRole`、`ScopeGrant` 解析出预期工作空间。
- 直接提交未授权 `workspace_key` 返回 403。
- 角色、组织、范围、账号停用或委托到期后，下一次读取立即重新授权。
- 工作空间读模型中的每项指标都能追溯到定义、时间、来源和证据。
- 多岗位用户可切换本人有效空间，不能切换到他人空间。
- CEO、经理、运营、平台管理员的 API、Agent、MCP 和 Worker 使用同一授权结果。

### 13.2 Web 测试

- 四个 P0 工作空间的默认路由、菜单和空/失败/无权限状态。
- 工作空间切换、范围筛选、刷新、下钻和返回上下文。
- 指标条、异常队列、待办队列、行动入口和证据抽屉的可操作性。
- Dialog/Drawer/ConfirmDialog/Toast 的成功、失败、校验、Esc、焦点和移动端行为。
- 1440、2515、390 宽度下无页面级横向溢出；宽表只在局部滚动。
- 3D 场景选中、双击、平移、缩放、复位和二维回跳；WebGL 降级后核心流程仍可用。

### 13.3 AI 与会议评测

- 同一问题在不同工作空间中输出重点符合岗位目标。
- 事实、推断、建议和未知明确分区；不存在无证据的指标结论。
- 分身不继承被模拟人员权限；跨部门读取和工具调用越权为 0。
- 会议所有角色使用同一证据快照，行动必须经过人工审批。
- 工作空间上下文、RoleTwin 版本、工具和证据快照可在运行详情复盘。

### 13.4 产品验收问题

产品负责人需要逐项确认：

1. 各岗位登录后的第一屏是否符合真实工作顺序。
2. CEO、经理、运营和平台管理员是否能一眼区分关注对象。
3. 是否仍能从首页自然进入数据中心、分析、会议和行动中心。
4. 是否存在重复页面、重复指标或岗位之间口径不一致。
5. 哪些模块应默认显示，哪些只在授权菜单中出现。
6. 3D 是否真正帮助理解关系；若无帮助，应保留二维入口而不是增加装饰。
7. 飞书/微信卡片是否能复用同一读模型而不暴露额外权限。

## 14. 变更控制与问题修正

后续开发发现以下问题时，必须先更新本指南的修订记录和对应任务，再改代码：

- 某岗位需要一个现有模型无法表达的业务范围或敏感字段。
- 首页指标与中心指标口径不一致。
- 需要第二套权限、菜单或行动状态机。
- 3D 场景需要直接写入外部系统。
- 企业自定义布局导致前端出现大量岗位分支。
- 同一工作空间在 Web、渠道和 Agent 上需要不同的授权解释。

修正优先级：先保持领域真值和授权边界，再调整读模型；先调整工作空间配置，再新增页面；只有出现独立扩容、独立生命周期或独立安全边界时，才考虑拆服务。

## 15. 完成定义

本次岗位工作空间改造完成，需要同时满足：

- 已有数据中心、知识、分身、会议、分析、行动和平台能力没有被复制或拆散。
- 至少四个 P0 工作空间由服务端配置和真实 Read Model 驱动。
- 岗位、权限、数据范围、RoleTwin 和首页投影边界清晰且有自动化测试。
- 首页可以下钻到现有中心并返回，不产生第二套业务对象。
- CEO、经理、运营和平台管理员的关注点不同，但指标口径和证据一致。
- 普通后台操作仍以二维表格、抽屉、弹窗和明确反馈完成。
- 3D 仅作为可降级的空间视图，不能成为核心数据或授权真值。
- 页面无说明性旁白，所有能力状态和错误可被直接识别。
- 开发、测试、验收和问题修正都能回溯到本指南的版本和任务编号。

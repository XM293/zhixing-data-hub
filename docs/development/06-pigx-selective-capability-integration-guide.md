# PigX 选择性能力吸收与知行数枢改造指南

- 文档状态：执行基线
- 更新时间：2026-08-30
- 适用范围：知行数枢当前模块化单体、企业管理台、身份权限、渠道、AI 运行和后续行动执行
- 参考来源：已授权的 PigX 5.9.0 微服务源码包（`pigx.zip`）
- 关联决策：`docs/architecture/adr/ADR-021-selective-pigx-capability-adoption.md`

## 1. 目标和结论

本指南用于约束后续 Codex 开发，避免因为参考了 PigX 而改变知行数枢的核心方向。

最终决策如下：

1. 知行数枢继续作为唯一的企业数据、指标、知识、记忆、数字分身、AI 运行、MCP 和行动真值平台。
2. PigX 只作为企业后台能力、成熟管理流程和交互模式的参考来源。
3. 吸收的功能使用知行数枢当前技术栈和自有契约重新实现，不直接依赖 PigX 的内部 ID、表结构、Spring Bean 或私有 API。
4. 不引入 PigX 的微服务基础设施作为首期前置条件，不提前增加 Nacos、Seata、Sentinel、Quartz、XXL-Job 或 Flowable。
5. 任何未来运行 PigX 服务或引入 PigX 代码的决定，都必须新建独立 ADR，并给出版本、许可证、运维和回滚方案。

这不是一次“框架替换”，而是一次“企业管理能力补强”。

## 2. 两个代码基线

### 2.1 知行数枢当前基线

知行数枢当前采用模块化单体：

- API：FastAPI、SQLAlchemy、Alembic、PostgreSQL/SQLite 开发模式。
- Web：Next.js、React、TypeScript、Tailwind、Lucide、Three.js。
- 后台任务：`BackgroundJob + Worker`，由统一任务契约管理重试、幂等和运行主体。
- AI：RoleTemplate、RoleTwin、EvidenceSnapshot、AgentRun、MemoryProvider、KnowledgeProvider、ToolGateway。
- 权限：`Enterprise`、`Principal`、`UserAccount`、`OrgUnit`、`Position`、`Membership`、`AccessRole`、`PermissionDefinition`、`RoleAssignment`、`ScopeGrant`、`AuthorizationDecision`、`IdentityManagementEvent`。
- 数据中心：规范电商事实、指标语义、来源映射、质量对账、客户 360、经营分析和驾驶舱。
- AI 工具：MCP 仅承担受控工具访问，业务授权和数据范围仍由内部应用服务执行。

当前身份管理纵向切片已覆盖：

- 平台管理员创建数据库账号。
- 配置体验角色、访问角色和逐角色数据范围。
- 账号状态、组织岗位、版本号和幂等请求。
- 防止管理员停用自身或扩大自身权限。
- 身份管理事件和授权决策分账审计。

后续仍需补强的主要部分：

- 企业级菜单覆盖配置、权限树可视化预览和复杂组织批量授权。
- 尚未纳入统一守卫的 Agent、Worker、Action 与业务 API 入口。
- SSO、正式渠道认证提供者和客户身份平台接入。
- 角色继承的适用条件；当前优先使用多个访问角色组合。
- 真实飞书/微信签名、通讯录同步、消息接收和发送。

重要边界：现有 `RoleTwin` 只代表岗位和表达能力，不得通过 PigX 的角色表为分身赋予账号权限。

### 2.2 PigX 参考基线

已审计的 PigX 5.9.0 工程具有以下能力：

- Spring Boot 3.5、Spring Cloud 2025、Java 17。
- Nacos 注册与配置、Gateway、OAuth2/Authorization Server。
- UPMS：用户、部门、岗位、角色、菜单、租户、社交绑定和日志。
- 通用能力：审计、日志、幂等、灰度、OSS、数据源、敏感词、字典和参数。
- Flowable 流程、Quartz/XXL-Job 任务。
- 报表、代码生成、微信、支付、监控等业务扩展。
- Vue 3、Element Plus、Pinia、动态路由和角色菜单投影。

Maven Reactor 的模块解析已通过，但源码包中没有可依赖的完整自动化测试体系。因此 PigX 的实现只能作为能力和交互参考，不能直接视为已通过知行数枢质量门。

## 3. 能力筛选矩阵

### 3.1 立即吸收并用当前技术栈重写

| 能力 | PigX 参考 | 知行数枢目标模块 | 优先级 | 处理方式 |
|---|---|---|---|---|
| 用户与账号 | `sys_user`、用户控制器 | `identity`、`auth` | P0 | 复用交互模式，使用 `Principal + UserAccount` |
| 部门与组织 | `sys_dept` | `identity` | P0 | 映射到 `OrgUnit`，保留层级和生效时间 |
| 岗位与任职 | `sys_post`、用户任职关系 | `identity` | P0 | 映射到 `Position + Membership`，不与访问角色混合 |
| 访问角色 | `sys_role` | `access` | P0 | 扩展为权限集合、数据范围、有效期和版本 |
| 菜单与按钮 | `sys_menu`、动态路由 | `navigation`、`access` | P0 | 菜单是权限投影，后端能力才是授权真值 |
| API/动作权限 | `@PreAuthorize` 等 | `access-control` | P0 | 统一覆盖 Web、API、Agent、MCP、Worker、Action |
| 审计与操作日志 | `sys_audit_log`、操作日志 | `audit`、`observability` | P0 | 保留主体、目标、范围、策略版本、request/run ID |
| 字典与系统参数 | `sys_dict`、公共参数 | `platform-config` | P1 | 只承载平台配置，不承载指标或制度真值 |
| 通知与站内消息 | `sys_message` 等 | `notification` | P1 | 先做内部通知，后续接入飞书渠道 |
| 文件元数据 | `sys_file`、文件组 | `object-storage` | P1 | 文件原件进对象存储，数据库保存元数据和权限 |
| 批量导入导出 | PigX 管理台模式 | `identity`、`data-center` | P1 | 所有导入必须有预览、校验、错误行和幂等键 |

### 3.2 只吸收设计，达到触发条件后再实现

| 能力 | 参考价值 | 暂缓原因 | 触发条件 |
|---|---|---|---|
| Flowable 工作流 | 审批节点、候选人和流程可视化 | 首期现有状态机足够，避免引入重运行时 | 出现跨天、补偿、人工中断和复杂分支流程 |
| Quartz/XXL-Job | 任务管理和失败重试界面 | 当前已有统一 Worker，不建立双调度器 | 任务规模或调度隔离证明现有框架不足 |
| 报表/JiMu | 报表筛选和布局交互 | 指标真值必须留在知行数枢语义层 | 指标和报表数量超过自有实现维护能力 |
| OAuth2/SSO | 登录和外部身份适配 | 需要适配当前 `ActorContext` 和企业身份边界 | 客户出现统一身份平台接入需求 |
| 代码生成 | CRUD 脚手架 | 不能让生成代码绕过领域契约 | 管理配置实体稳定且重复 CRUD 达到规模 |
| 灰度发布 | 运维发布参考 | 不属于当前产品领域 | 多版本在线服务和独立发布团队形成 |

### 3.3 明确不吸收

- Nacos、Spring Cloud Gateway、Seata、Sentinel 作为知行数枢首期运行前置条件。
- PigX 的 `sys_*` 数据库作为企业、人员、指标或知识的事实来源。
- PigX 的租户模型直接替代知行数枢的 `Enterprise` 和 `ScopeGrant`。
- Quartz 与 XXL-Job 同时接入现有 `BackgroundJob + Worker`。
- PigX 报表库直接替代规范经营事实和指标语义层。
- 微信、支付等与当前首期目标无关的业务模块。

### 3.4 管理台交互吸收矩阵

PigX 的管理台价值不仅是功能清单，也包括列表稳定、覆盖层编辑、危险操作确认和统一消息反馈。知行数枢不复制 Element Plus 页面，但必须在当前 React 视觉系统内遵守同等交互纪律：

| 操作类型 | 知行数枢实现 | 列表与表单状态 |
|---|---|---|
| 小型新增、编辑 | 统一 `Dialog` | 列表不移动，成功后关闭并刷新 |
| 账号、角色、委托等复杂配置 | 统一右侧 `Drawer` | 保留原页面上下文，可滚动编辑 |
| 删除、停用、解绑、换绑、撤销、审批、批量写入、重试 | `ConfirmDialog` | 执行前显示对象、影响和必要原因 |
| 创建或保存成功 | 全局 Success Toast | 不在页面顶部插入成功横幅 |
| 普通写入失败 | 全局 Error Toast | 覆盖层保持打开，用户输入不丢失 |
| 字段校验失败 | 字段内联错误 | 聚焦第一个错误字段 |
| 查询或首次加载失败 | 内容区错误状态与重试 | 不阻断页面其他可用部分 |
| 权限、只读和持续风险 | 页面内联状态 | 保持可见且可被复核 |

统一覆盖层必须具备 Portal、焦点回收、Tab 焦点约束、Esc 关闭、背景滚动锁定、`aria-modal` 和移动端适配。新页面不得复制局部遮罩和消息实现。

## 4. 目标架构

```text
┌──────────────────────────────────────────────────────────┐
│ Web / 飞书 / 后续企业微信 / 服务账号                       │
└───────────────────────┬──────────────────────────────────┘
                        │ 认证声明
┌───────────────────────▼──────────────────────────────────┐
│ 知行数枢身份与授权控制面                                  │
│ Principal / Account / Org / Position / AccessRole         │
│ Permission / ScopeGrant / ActorContext / Audit            │
└───────────────┬───────────────────────┬──────────────────┘
                │                       │
      ┌─────────▼─────────┐   ┌─────────▼──────────────────┐
      │ 平台管理能力       │   │ 数据与 AI 核心域             │
      │ 用户组织菜单配置    │   │ 事实/指标/知识/记忆/分身      │
      │ 通知文件导入审计    │   │ 会议/分析/MCP/行动            │
      └─────────┬─────────┘   └─────────┬──────────────────┘
                │                       │
                └──────────┬────────────┘
                           │ 自有契约
                 ┌─────────▼─────────┐
                 │ Background Worker │
                 │ Connector / Agent │
                 │ Action / Evaluation│
                 └───────────────────┘
```

PigX 的源码位于只读参考边界之外。知行数枢不开发 PigX 专用导入适配器、不运行 PigX 侧车，也不把 PigX 服务或数据库纳入产品运行依赖。

### 4.1 唯一事实来源

- 身份、访问范围和 AI 执行主体：知行数枢身份授权模型。
- 经营事实和指标：知行数枢规范事实及指标语义层。
- 正式制度和知识版本：知行数枢知识生命周期。
- 角色记忆：知行数枢候选、审核和版本系统。
- 运行、证据、行动：知行数枢 `AgentRun`、`EvidenceSnapshot`、Action 领域。
- PigX 只提供能力和交互参考，不成为上述真值或运行输入。

### 4.2 认证和授权原则

1. 登录方式可以由本地认证或外部 SSO 提供，但进入领域层前必须转换为可信 `ActorContext`。
2. 客户端不能提交 `principal_id`、角色或数据范围来替换服务端身份。
3. 菜单隐藏只改善体验，API、MCP、Worker 和 Action 必须再次授权。
4. RoleTwin 不继承被模拟人员的访问角色；分身可用能力是调用者权限、分身边界、渠道能力和工具策略的交集。
5. 外部写操作必须先形成 ActionProposal，经过职责分离审批，并在执行前重新授权。

## 5. 数据模型映射规则

| PigX 概念 | 知行数枢概念 | 迁移规则 |
|---|---|---|
| `sys_user` | `Principal + UserAccount` | 生成内部稳定 ID，保留源系统 ID 映射，不把用户名当主键 |
| `sys_dept` | `OrgUnit` | 迁移父子关系和状态，补充 `enterprise_id`、生效时间和历史引用 |
| `sys_post` | `Position` | 只表达岗位，不代表权限 |
| `sys_role` | `AccessRole` | 角色权限重新绑定到 `PermissionDefinition` 和 `ScopeGrant` |
| `sys_menu` | 菜单投影 | 转换为资源/动作/导航投影，不能只依靠前端菜单授权 |
| `sys_role_menu` | 角色权限关系 | 逐项映射并验证资源动作是否存在 |
| `sys_user_role` | `RoleAssignment` | 写入分配主体、分配人、有效期和版本 |
| `sys_user_dept` | `Membership` | 明确主组织、兼职组织和生效时间 |
| `sys_user_post` | 任职关系 | 绑定岗位和组织，保留历史记录 |
| `sys_tenant` | `Enterprise` 参考输入 | 只有一对一且语义相同才允许映射，不能默认等同 |
| `sys_audit_log` | `IdentityManagementEvent` / 授权审计 | 只导入可解释字段，不能伪造历史授权决策 |
| `sys_social_details` | `ChannelIdentity` | 只保留外部身份映射和生命周期，不让渠道系统成为主体真值 |
| Quartz/XXL-Job 表 | `BackgroundJob` | 只做状态和配置转换，不同时运行两套调度器 |
| Flowable 表 | 后续 Workflow 模块 | 达到触发条件后单独设计，不提前建核心表 |

所有迁移必须是显式的 Alembic 前向迁移或一次性导入命令，禁止直接把 PigX SQL 作为知行数枢初始化脚本。

## 6. 分阶段改造计划

### 阶段 A：基线冻结和契约对齐

关联现有任务：`DOM-001`、`IAM-001`、`FND-007`。

工作内容：

- 固定 `Principal`、`UserAccount`、`Enterprise`、`OrgUnit`、`Position`、`AccessRole`、`RoleTwin` 的边界。
- 补充菜单、按钮、API、MCP 工具到资源/动作权限的映射规则。
- 明确 PigX 参考模块和当前不引入模块清单。
- 为外部身份保留 `ChannelIdentity` 接口，但不提前接入具体渠道。
- 建立一组 PigX 脱敏结构样例，只用于映射和契约测试。

验收：契约可验证；任意功能都能回答“谁能做、对什么做、在哪个范围做、由谁审计”。

### 阶段 B：身份、组织和权限后端完善

关联现有任务：`IAM-002`、`IAM-003`、`IAM-004`、`IAM-007`、`FND-007`。

工作内容：

- 完成本地密码登录、服务端会话失效和可替换认证提供者接口；SSO 与外部渠道身份通过后续提供者接入。
- 完善组织、岗位、任职的创建、调整、停用和历史查询。
- 完善访问角色、权限绑定、逐角色数据范围和冲突策略。
- 增加权限检查解释、权限预览和有效期判断。
- 让 API、Agent、MCP、Worker、Action 全部使用统一授权守卫。
- 记录身份变更、授权允许/拒绝、主体快照、策略版本和 request/run ID。

验收：同一主体从 Web、API、MCP 和 Worker 进入时得到一致授权结果；修改角色或组织后，历史运行仍能按旧快照复盘。

### 阶段 C：管理台菜单和运营界面

关联现有任务：`IAM-005`、`UIA-002`、`UIA-004`。

工作内容：

- 完成用户、组织、岗位、访问角色、菜单、权限、审计页面的真实数据库读写。
- 使用后端返回的导航投影生成菜单，前端只负责展示和路由体验。
- 增加权限树、范围选择器、权限解释、变更预览和操作确认。
- 保持知行数枢数据中心视觉语言：密集可扫描、全宽工作区、清晰状态和证据链。
- 所有页面实现加载、空数据、失败、无权限、过期和并发冲突状态。

验收：平台管理员可完成一次“创建账号 → 绑定组织岗位 → 分配访问角色 → 授权门店范围 → 查看审计”的端到端流程。

### 阶段 D：专用适配路线关闭

决策：不开发 PigX REST、导出文件或数据库专用导入适配器，不建立 PigX 管理侧车，也不维护 PigX 到知行数枢的长期身份映射协议。

通用批量交换中心只接受知行数枢自有数据集契约。未来客户若需要从任意旧系统迁移数据，按客户实际结构创建一次性迁移任务或通用连接器，不以 PigX 命名，不让源系统字段和 ID 进入上层领域。

### 阶段 E：通用平台能力补强

关联现有任务：`OPS-001`、`OPS-002`、`OPS-003`、后续新增平台任务。

已在迁移 `0044_platform_management_controls` 中实现：

- 平台配置和字典中心。
- 本地对象存储适配、文件元数据、完整性校验和权限感知下载。
- 站内通知、领域事件、渠道投递状态和未读状态；真实飞书/微信发送仍等待渠道接入。
- 通用 CSV 导入预检、错误行、确认写入和导出文件。
- 数据库后台任务详情、Attempt 时间线和受控重新排队。
- 组织子树授权、临时委托、权限解释和统一平台操作审计。

这些能力只能服务于平台配置和运维体验，不能把指标、制度、记忆或经营事实塞入通用配置表。

### 阶段 F：可选复杂能力评估

只有出现真实需求后，才分别创建 ADR 和任务评估：

- Flowable：复杂审批、跨天恢复、补偿和人工中断。
- Temporal：跨系统长事务、重试和补偿显著超过现有 Worker 能力。
- JiMu/报表平台：自有驾驶舱和指标语义无法经济维护时。
- 外部 OAuth/SSO：客户身份平台接入成为部署前置条件时。
- 独立外部管理系统：客户明确要求保留既有系统时，按外部系统契约单独评估，不默认采用 PigX。

## 7. 数据库和迁移规则

1. 新表必须通过 Alembic 迁移创建，核心表携带 `enterprise_id`。
2. 外部来源只通过 `source_system + external_id + mapping_version` 关联。
3. 账号、角色、组织和菜单使用状态字段和不可变事件记录，不物理删除有历史引用的对象。
4. 写操作必须支持幂等键和乐观版本，重复请求不得重复产生审计事件。
5. 迁移脚本提供前向修复或最小回滚说明；不得依赖手工修改生产数据库。
6. 不提供 PigX 专用导入路径；通用迁移也不得直接写入 AI、指标、知识和记忆表。
7. 外部身份密钥、密码、令牌和连接凭据只从运行时密钥管理读取，禁止进入文档、种子或日志。

## 8. 质量门槛和验收集

### 后端

- 组织树、岗位任职、角色分配、菜单权限、数据范围各有单元测试。
- 权限矩阵覆盖 CEO、部门经理、员工、平台管理员、角色分身和服务账号。
- 允许、拒绝、显式拒绝优先、范围交集、失效时间和版本冲突有集成测试。
- API、MCP、Worker 和 Action 使用同一授权结果的契约测试。
- 通用批量交换样例覆盖重复请求、缺失字段、无效数据、错误行和确认写入。

### Web

- 管理员端到端验收路径必须真实读写数据库。
- 菜单隐藏、直接访问 URL、手工构造 API 请求都要验证服务端拒绝。
- 桌面和移动端覆盖列表、详情、抽屉、权限树、错误和无权限状态。
- 任何模拟数据必须保留测试来源，不能伪装成客户生产数据。

### AI、MCP 和行动

- 分身不能因被模拟人员身份而扩大调用者范围。
- MCP 工具必须声明资源、动作、风险等级和范围解析。
- AI 生成的操作只能进入草稿或行动提议，不能绕过审批写回任何外部系统。
- 运行记录保存实际 Actor、权限策略、证据和配置版本。

## 9. Codex 执行协议

后续每个改造任务执行前，必须按以下顺序：

1. 读取本指南、关联 ADR、任务索引和目标模块的局部规约。
2. 说明本次只修改的领域、契约、迁移、页面和测试范围。
3. 先补 Schema、映射样例或失败测试，再实现代码。
4. 不在 `references/open-source` 中开发，不整包复制 PigX，不引入未批准的运行时依赖。
5. 完成单元、集成、契约和 UI 验证后，更新相关文档和任务状态。
6. 最终交付必须说明已吸收的 PigX 能力、未吸收的能力、验证证据和剩余风险。

出现以下情况时必须暂停并新增 ADR，而不是直接扩张范围：

- 需要引入 Nacos、Seata、Sentinel、Flowable、Quartz 或 XXL-Job。
- 需要让 PigX 或其他外部管理数据库成为身份或业务事实来源。
- 需要建立第二套权限、菜单或任务系统。
- 需要让 AI 或 MCP 直接调用 PigX 内部服务绕过知行数枢授权。
- 需要复制大段 PigX 源码，或者引入新的许可证和分发义务。

## 10. 完成定义

本改造方向达到阶段性完成，必须同时满足：

- 知行数枢核心数据、AI、MCP 和行动架构未被 PigX 基础设施替换。
- 用户、组织、岗位、角色、菜单、审计等选定能力在当前技术栈中可用。
- 权限同时覆盖功能、数据范围、对象、AI 主体和工具动作。
- 管理台可完成真实的人员和权限运营流程。
- 数据库迁移、通用批量交换、授权和 UI 主流程均有可重放测试。
- PigX 只作为可追溯的参考来源，产品代码依赖自有契约。
- 后续 Codex 可以根据任务索引逐个实现，而不需要重新解释总体边界。

## 11. 当前实施进度

截至 2026-08-30，已完成第一批 P0 管理目录纵向切片：

- 组织单元创建、更新、版本控制、父子循环检查和生效岗位停用保护。
- 岗位创建、更新、版本控制、组织归属校验和生效任职停用保护。
- 访问角色创建、更新、权限目录校验、权限集合替换和修订号控制。
- 目录操作使用独立 `IdentityCatalogEvent`，与账号管理事件和授权决策分账。
- 管理台组织、岗位和访问角色页面已从只读投影升级为真实数据库编辑工作区。
- 管理台权限编辑使用 API 返回的权限目录，不在页面硬编码权限全集。
- 后端按权限返回导航工作区和菜单项投影，前端用该投影渲染中心菜单和二级页签；菜单仍是授权结果，不替代 API 守卫。
- 已提供 `/api/v1/auth/login`、`/api/v1/auth/session` 和 `/api/v1/auth/logout`，本地密码只保存 PBKDF2 哈希，会话可被账号停用或主动注销；开发身份接口仅为兼容自动化测试，正式 SSO 和渠道认证仍未接入。
- 数据中心概览、来源、同步、实体、指标、质量、经营事实和客户 HTTP 入口已经解析同一可信身份并调用统一授权决策服务；管理类资源要求企业范围，经营查询按企业或门店范围检查，允许和拒绝都进入 `AuthorizationDecision`。
- 数据中心菜单投影已按后端真实权限对齐：来源和同步只对 `source.manage` 可见，实体/指标/质量使用 `metric.definition.read`，经营事实和客户分别使用查询与客户读取权限；门店角色默认进入获授权范围。
- 自动巡店后台任务已升级到任务 v2：保存发起人快照、权限版本、声明权限和目标范围，Worker 领取使用一次性哈希令牌，内部 API 不接受主体参数并在执行前按当前数据库权限和范围重新授权；排队后撤销旗舰店范围会拒绝执行并留下授权审计。
- 企业 MCP 网关已升级为短期受限会话：签发时固定客户端、工具白名单、范围上限、主体快照、权限版本和可选 AgentRun，令牌只存哈希；工具目录和每次调用按当前数据库账号重新授权，MCP 不能传主体、角色、权限或企业参数，范围和权限变化立即在下一次调用生效。
- PigX 的统一日志检索交互已按知行数枢契约重写：管理员在一个工作台检索授权、身份、MCP、工具、Worker、Agent、行动和平台操作八类现有事实，支持企业隔离、来源/结果/主体 Facet、追踪 ID、时间、文本和分页；实现不复制 PigX 日志表，也不建立第二套审计真值。
- 渠道身份绑定已按自有契约形成数据库纵向切片：未知外部身份只保存哈希与短提示，可绑定、换绑、解绑、停用和启用；配置使用乐观版本、幂等请求和追加式事件，同一渠道租户内阻止内部主体重复绑定。
- `/console/admin/channels` 已从原型升级为真实管理工作区，支持组合筛选、身份目录、配置编辑与变更事件；已绑定内部账号会在同租户其他身份的选择器中直接禁用，后端唯一约束继续作为最终防线。
- 渠道身份事件已纳入统一审计投影，允许清单只暴露渠道和状态变化，不返回外部身份原文；身份解析后仍重新读取本地账号、角色和数据范围。
- 迁移 `0044_platform_management_controls` 新增平台操作事件、参数字典、领域事件、通知与投递、文件资产、批量交换行和临时访问委托；全部核心记录保留企业边界、主体、请求键、request/run ID 或版本信息。
- `/console/admin/jobs` 已接入数据库任务筛选、详情、载荷、Attempt 时间线和失败任务受控重新排队；旧 Attempt 不删除，重试要求终态、预期执行次数、原因、幂等键和 `operations.run.manage`。
- `/console/admin/config`、`/console/admin/files`、`/console/admin/exchange` 与 `/console/inbox` 已替换为真实数据库工作区；文件内容进入可替换的本地对象存储适配器，批量交换支持 CSV 预检、逐行错误、确认写入和导出。
- `OrgUnit` 子树已进入服务端范围判断；临时委托只允许委托人的当前直接权限和范围子集，解析身份时重新检查委托人的现行角色权限，撤销或到期后下一次请求立即失效。
- 权限解释返回直接角色、直接权限、委托权限、有效权限、范围和活动委托；平台操作事件已作为第八类来源进入统一审计中心。
- PigX 专用导入适配器与侧车路线已正式删除。通用批量交换只依赖知行数枢自有数据集契约。

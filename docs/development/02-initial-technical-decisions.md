# 首期技术决策草案

这些决策用于启动任务拆解，不代表不可修改。任何改变系统边界、关键依赖或数据模型的决定都应新增 ADR。

## TD-001 模块化单体优先

- 决策：Web、API和Worker使用一个仓库和统一领域包，按模块隔离。
- 原因：首期团队和业务量不足以支撑微服务成本。
- 拆分触发：独立扩容、独立发布、故障隔离或团队所有权出现可测需求。

## TD-002 PostgreSQL作为首期主数据库

- 决策：配置、领域元数据、知识元数据、记忆、运行记录和小规模经营事实先使用PostgreSQL。
- 扩展：语义向量使用pgvector或知识组件内置能力；对象文件放MinIO。
- 迁移触发：分析数据量和查询并发超过已定义SLO后引入专用分析存储。

## TD-003 前后端候选栈

- 管理台：Next.js、TypeScript、React。
- 业务API与AI/数据服务：Python、FastAPI、Pydantic。
- 后台任务：首期使用 PostgreSQL 任务表和通用 Worker；可靠跨天工作流出现后评估Temporal。
- 接口：OpenAPI + JSON Schema，事件使用版本化Envelope。

最终脚手架由任务 `FND-004` 通过ADR确认。

## TD-004 自有领域契约优先

上层只调用自有 `KnowledgeProvider`、`MemoryProvider`、`MetricService`、`AgentRuntime` 和 `ToolGateway`。开源项目通过Adapter接入。

## TD-005 知识产品双跑

WeKnora作为首选知识POC，RAGFlow作为解析与检索对照，OpenViking作为资源上下文与层次检索对照。三者使用同一组当前生效制度切片和固定问题评测，按引用准确性、解析质量、版本能力、上下文组织、接入成本和延迟决定；平台知识真值不迁移到任一供应商。

## TD-006 记忆先自建状态流

首期先实现 `candidate → approved/rejected → active/retired` 状态流，再接入TencentDB-Agent-Memory或Mem0做存储/抽取对照。这样角色治理不受记忆后端限制。

## TD-007 Codex运行时优先但不锁定

首期实现Codex适配器；领域对象不保存Codex特有结构。运行时事件转换成企业自有 `AgentRunEvent`。

## TD-008 MCP只暴露业务能力

每个MCP工具调用一个内部应用服务。禁止暴露通用任意SQL、任意HTTP或生产Shell工具给业务智能体。

## TD-009 先接一条真实结构化数据链路

首期至少接入一个店铺/业务单元的销售、退款、广告和库存日级数据，验证实体映射、指标语义、证据快照和角色问数。

## TD-010 全链路可观测但首期简化

每次回答记录run_id、角色版本、Prompt版本、模型、工具、证据快照、延迟、Token/成本和用户反馈。首期可存数据库，后续再引入专业追踪平台。

## TD-011 私有化单企业部署但保留企业边界

首期不建设 SaaS 多租户运营后台，但企业身份、数据、知识、运行、任务和审计对象都携带稳定 `enterprise_id`。子公司、部门和店铺通过组织与数据范围建模。

## TD-012 身份概念和智能角色分离

人员账号、岗位、`AccessRole` 和 `RoleTwin` 分别建模。岗位不自动等于权限，RoleTwin 不保存访问角色，也不能把被模拟管理者的权限授予提问者。

## TD-013 认证适配、统一授权

本地开发使用最小管理员认证，生产认证通过飞书或 OIDC 适配器接入。API 建立可信 `ActorContext`；RBAC 与数据范围组合授权；Web、MCP、Worker 和 Action 复用同一授权应用服务。

## TD-014 菜单是能力投影

管理台壳子根据后端返回的当前主体能力生成导航和操作入口。前端路由守卫只改善体验，后端权限和数据范围检查是最终边界。

## TD-015 授权审计独立于运行日志

权限变更、授权允许或拒绝、临时委托、渠道绑定和关键审批形成结构化审计记录。日志平台负责运输和检索，不替代领域审计。

## TD-016 产品全景原型先于领域实现

FND-004 应用骨架完成后，先用版本化 UI Read Model、统一 Fixture 和可替换模拟数据源构建产品全景。产品负责人通过 `UIA-006` 验收后再执行 `DOM-001`。该步骤只冻结产品信息架构和首批体验，不改变既有领域边界，也不将页面模型直接固化为数据库结构。

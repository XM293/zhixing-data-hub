# M0：身份、权限与管理台壳任务包

## 目标

建立所有 Web、飞书、Agent、MCP、Worker 和 Action 共用的企业身份与授权底座。首期不追求复杂 IAM 产品，但必须保证不同岗位、部门和店铺范围的用户看到一致且受控的数据与能力。

## 核心原则

1. `AccessRole` 是访问权限集合，`RoleTwin` 是智能角色资产，二者不得混用。
2. 私有化部署仍保留 `enterprise_id`，但首期不建设 SaaS 多租户运营平台。
3. 菜单只投影有效权限，API 和领域服务才是授权边界。
4. Agent、MCP 和后台任务必须携带可信 `ActorContext`。
5. 分身能力只会收窄调用者权限，不会提升调用者权限。
6. 授权决策和关键权限变更必须可审计。

## 执行顺序

```text
DOM-001 → IAM-001 → FND-007 → IAM-002
                        ├────→ IAM-003 → IAM-005
                        │          └────→ IAM-007
FND-006/FND-008 → FND-010 ─────────────→ IAM-004
CHN-001 + IAM-002 ─────────────────────→ IAM-006
```

## 任务组

- `FND-007`：企业、用户、组织、岗位和任职基础模型。
- `FND-010`：通用 Worker 与 PostgreSQL 后台任务框架。
- `IAM-001`：身份和访问控制公共契约。
- `IAM-002`：本地认证、会话和认证提供者适配接口。
- `IAM-003`：访问角色、数据范围和 ActorContext 授权服务。
- `IAM-004`：API、MCP、Agent 和 Worker 统一授权守卫。
- `IAM-005`：管理台应用壳、授权菜单和路由状态。
- `IAM-006`：飞书等渠道身份映射与账号绑定。
- `IAM-007`：授权决策与关键管理操作审计。

## 验收演示

管理员创建企业、部门、岗位、用户和店铺范围访问角色。员工登录后只看到获准菜单，并通过 CEO 分身询问制度；回答只使用员工有权读取的制度。部门经理可以查询本部门店铺数据但无法访问其他部门。飞书已绑定用户获得同样结果，未知身份进入绑定流程。所有允许、拒绝、权限变更和关键审批均可按主体与运行 ID 查询。

## 退出条件

- Web、API、Agent、MCP Mock 和 Worker Mock 使用同一授权用例。
- 匿名、无权限、跨部门、权限撤销和临时委托场景有自动化测试。
- RoleTwin 不保存或继承人员访问角色。
- 菜单与按钮权限不会成为唯一授权检查。
- 一次问答或行动能够还原发起人、执行主体、策略版本和授权结果。
